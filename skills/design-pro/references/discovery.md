# Intent discovery and project context

Start from the decision the user needs to make. A spacing question needs its platform and affected controls, not a product strategy interview. A new multi-screen application needs users, tasks, essential journeys and constraints before screen design.

## Find the next useful question

Read the current request, established conversation decisions, provided brief, applicable project instructions and existing patterns. Separate direct user statements from inferred requirements and demo assumptions.

Prioritize gaps that change the outcome:

- **Intent:** create, improve or resolve what? What will the user be able to do afterward?
- **People and setting:** who performs the main task, where, under what interruptions or accessibility needs?
- **Task and scope:** what initiates the flow, what counts as done, and what is excluded?
- **Platform and constraints:** native/mobile web/desktop, existing stack, design system, content and asset availability.
- **Direction:** meaningful brand attributes and references, including what the user likes about them.
- **Success and deliverable:** observable outcome; advice, review, proposal, runnable prototype or implementation.

Ask the highest-impact unanswered question, one at a time. Offer two or three choices only if they make the decision easier; permit a free-text answer. After each answer, update what is known and choose the next gap. Do not repeat a fixed questionnaire.

Stop when remaining uncertainty can be explicitly recorded without compromising the requested work. A user can ask for a preliminary proposal before every detail is settled. Mark assumptions, their consequences and any point where they must be resolved.

For a consequential flow, describe a complete job before choosing its controls: who needs what result, where the input comes from, and what must happen afterward. Use realistic content where length/similarity affects identification. A task states the desired result; a scenario describes one proposed design's actions and responses. A few representative tasks do not prove every workflow is covered. These distinctions refine discovery without adding a compulsory questionnaire. [U06, PDF pp. 31–45](books/U06.md#design-an-entire-task-including-its-boundaries)

Connect the brief to a small set of [design criteria](concepts/strategy-and-criteria.md): what the proposed experience must let people accomplish, under which conditions, and what evidence would demonstrate that. Keep criteria distinct from a requested feature list. Existing research/history can prevent redundant questions; a provisional assumption remains provisional even if everyone agrees. [X11, pp. 17–27, 41–52, 56–65](books/X11.md)

## Reconcile a correction

Apply the user's latest explicit correction. Describe material consequences for screens, interactions or constraints. If it conflicts with another still-active requirement, ask about that conflict rather than silently choosing. Preserve prior decisions as superseded only when history is useful; keep the current brief clear.

## Persistence

Use an established project documentation location where one exists. Otherwise a project-local `design-brief.md` is sufficient when file writing is authorized. Store factual project context there, not in the reusable skill or source notes. Do not treat ordinary project persistence as a request to change global memories.

If context is unavailable, report the gap and ask the smallest useful question. Do not fabricate previous user answers.

## Research basis

This interview procedure is a design-pro synthesis. Context, motivation and purpose precede interface assessment in [M02](books/M02.md#research-selection). It is not a claim that a design conversation replaces research with representative users.

Adapt the process to constraints and connect the problem, use context and proposed outcome instead of generating documents by habit. The process-map questions and linked-artifact examples support this selective approach. [X01, pp. 6–16, 22](books/X01.md)

When a user requests a feature, distinguish the underlying problem from that particular solution and account for navigation/maintenance cost. Define a useful outcome before selecting a measure; longer sessions can be worse for a task intended to finish quickly. [X03, pp. 3–10](books/X03.md)

Existing-product context should include current tools, workarounds, actual content and delivery constraints when these affect design. Reuse the information already available rather than asking the user to reconstruct it. [X04, pp. 7–15](books/X04.md)

Use a story for the desired action/outcome, a scenario for its circumstances, and a flow for paths through the product. A persona, sitemap or journey map is optional when it adds useful understanding; project facts and observed research remain distinct from templates or fictional examples. [X06, pp. 11–19, 28](books/X06.md)

For an unclear new-product intent, ask about the triggering situation, current workaround and desired improvement before adopting a suggested feature as the goal. Job statements and stories supply that distinction in [M05, pp. 20–37](books/M05.md#intent-situations-and-discovery). Do not force purchase-history interviewing onto every design request or invent emotional motives from the author's examples.
