# U09 — Web UI Design Patterns 2014

**Source:** *Web UI Design Patterns 2014: A Deeper Look at the Hottest Websites and Web Apps Today*, UXPin. Chris Bank signs the introduction, co-written by Waleed Zuberi (p. 8). Original filename: `User Interface/Web UI Design Patterns 2014.pdf`. Locators are PDF pages, matching the visible page numbers.

**Review:** all text pp. 1–191 read; 175 relevant original pages inspected, including all pp. 101–191. The separate coverage ledger lists exact image pages. Static screenshots establish visible composition and labels, not runtime behavior or current service capabilities.

## Patterns describe a problem and conditions, not a finished feature

The opening distinguishes a reusable solution from a plug-in feature or finished design, and asks for the problem, solution, example and appropriate usage (pp. 7–10). Preserve user navigation, inputs, data/integration boundaries, defaults, audience and context. A screenshot may need a flow and annotations to explain the solution. The book calls patterns generally platform-agnostic; the implementation still needs device/input-specific behavior. A single-sentence problem is a useful starting point, not a limit on necessary context or exceptions.

## Adapt to the actual environment

The responsive discussion considers orientation, images/crops, navigation, hierarchy, available features and changed interaction (pp. 12–16). The original diagram shows desktop-to-phone arrangements; it does not prove the pictured dimensions are required breakpoints. Reject the claim that every device model needs a separate product from scratch or that one platform is inevitably replacing another. Reuse the task foundation and adapt where constraints actually differ.

Large screens can support list/detail simultaneously, contextual editing and larger meaningful content without filling all available space (pp. 15–16). The authors also favor optional one-/two-hand use. Do not assume every phone is one-handed or every larger device is held with two hands, or adopt emotional “realness” claims as demonstrated effects. Contextual controls and modes need a clear current state and exit; hiding every unavailable action can also remove useful context. Fewer features is not inherently a complete answer to a necessary complex workflow.

### Input and navigation decision rules

Default values and autocomplete can reduce repetitive entry or expose possible results, but defaults need visible meaning and correction (pp. 51–53). A location does not establish someone's language, identity or desired country code. An autocomplete list needs a defined selection/dismissal path; the source's speed claim is not a measured result for this product.

Trying useful functionality before registration can let someone assess fit, but deferred authentication is not always suitable (pp. 54–57). Preserve work across any later account boundary and disclose persistence/limitations. Do not require signup for a demo merely because a historical site does. Neither immersion nor a walkthrough is universally better.

The social-login passage lists historical providers and frames fewer passwords/profile entry as convenience (pp. 58–59). It does not settle current provider availability, protocol choice, permissions or integration security. Do not interpret “less worry about password security” as freedom from responsibility for account, session or consent behavior. These demos need no live identity integration.

Badges/dots/banners can indicate new activity, but the signal needs understandable meaning and appropriate interruption level (pp. 60–61). A hidden hover control or click-and-hold preview is not automatically discoverable to every input method (pp. 62–64). Keep required content/actions available without hover or secret gestures. Rarity alone is not a reason to hide recovery.

Expandable controls can save space while retaining a clear trigger, state and usable focus path; a growing text field must leave the rest of the task reachable (pp. 65–66). Undo can support reversible actions and reduce repetitive confirmation, but the claim must match actual reversibility (pp. 67–69). Editing text does not necessarily retract a message already sent to someone. Irreversible external consequences need their own decision.

Jump links can restore orientation in long content (pp. 71–72). A single-page app can preserve ongoing context such as playback, but asynchronous loading is not inherently instantaneous or faster; URL/deep-link/back behavior still matters, as the source itself notes (pp. 73–76). The pattern does not require this stack for a public game page.

Distinguish personalized recommendations, related content and editorial/paid featuring (pp. 77–90). Explain why an item is shown and label promotion honestly; popularity or recommendation does not prove suitability/truth. Next steps should help an unfinished user goal rather than endlessly extending sessions. History can support return/resumption, but an activity feed, recently viewed item and intentional bookmark have different meanings and retention expectations.

Infinite scroll may suit exploratory browsing, but the authors identify orientation, jumping and return/bookmark problems (pp. 91–94). A top button does not solve every one of those. Define loading/error/end behavior and access to surrounding controls before adopting it. Walkthroughs/coach marks can support a new task but do not justify collecting extra data or forcing a tour for every user (pp. 95–98). The text praises a setup bot; no bot was tested here.

Overflow menus can hold contextually secondary actions, but are not an excuse to accumulate unwanted features or privilege sharing solely for engagement (pp. 99–101). A morphing/toggle control should communicate its present state and next effect; “like/unlike” does not prove any operation is reversible (pp. 102–103). Sticky navigation should retain access without covering content/focus. Vertical navigation is a layout option, not a novel replacement for every other approach (pp. 104–108).

The book mixes popover, modal and window terminology (pp. 109–111). Decide actual modality, entry, dismissal, focus and restoration rather than borrowing only its name. A tap/swipe-only dismissal is insufficient as a universal interaction. Sidebars/drawers need a recognizable trigger, current location and return path; not everything placed in a drawer becomes unimportant (pp. 112–115). Links to content should have an understandable effect; navigating to an artist and sorting a column header are not the same operation even though the source groups them together (pp. 116–117).

The original pp. 101–117 show Pinterest category navigation/toggles, Spotify play/pause and search drawer, Houzz/Facebook header views at different scroll positions, Facebook side links/content preview, Pinterest signup overlay, Medium/NYTimes side navigation and Asana content links. These illustrate state and placement; the signup overlay and content preview do not establish identical modality. Current-state cues and actual focus/dismissal still need runtime checks.

## Social actions require explicit meaning and audience

The social gallery has been inspected. Medium/Vimeo/Facebook feeds (pp. 124–126), Goodreads friends and Spotify suggested follows (pp. 127–128), Google+/Quora/Pinterest/Spotify follow choices (pp. 129–131), and Medium/Reddit/Stack Overflow/Quora endorsement controls (pp. 132–134) illustrate distinct activity/relationship/curation mechanisms. They do not prove underlying ranking, completeness or actual delivery.

The badge gallery shows Codecademy course badges and a Stack Overflow profile (pp. 119–120). Auto-sharing screenshots show Quora post destinations, Twitter account connection, Spotify activity/privacy options and Vimeo connection controls (pp. 121–123); these are visible settings, not proof of consent or successful publication. Quora starts the feed gallery on p. 124.

Badges/achievements describe progress but do not prove competence, useful habits or improved engagement; arbitrary profile collection is not a user goal (pp. 119–120). For automatic sharing, the source's assumption that people would share anyway is not authorization (pp. 121–123). Show audience, content and action scope; do not automatically publish activity or add sharing to these demos. Activity feeds, friendship, following, voting and liking have different purposes/visibility (pp. 124–134, 140–143). Keeping a person “busy” is not evidence of usefulness, and votes/likes are not proof of truth or quality.

The “binary rating” passage conflates liked/not-liked with liked/disliked; an absence of endorsement is not necessarily a negative rating (pp. 140–141). Relationship types, unsubscribing, collection visibility and reversal need explicit semantics. Finding friends does not authorize importing contacts or sending invitations; neither conversation navigation nor a fictional chatbot requires a social graph (pp. 142–143).

Pay-to-promote describes purchased visibility, not neutral popularity or an inherent benefit to every viewer (pp. 135–137). Distinguish promotion from organic content and show actual terms if such a feature exists. Historical service offers are not verified current options. Direct messaging is intended as private communication in the text (pp. 138–139), but an interface label alone does not establish confidentiality, retention or who can access a message. Do not assume people are comfortable sharing more private information.

The gallery actually mixes different incentives: Quora shows credits to request an answer, OKCupid/Facebook show monetary promotion choices, and Stack Overflow shows a **reputation bounty** (pp. 135–137). These are not all the same paid-advertising model. Spotify's two-pane messages and Twitter's message dialog illustrate conversation/context and composer placement; they do not show AI behavior, error handling or privacy guarantees (pp. 138–139). Pinterest's Unlike state differs from a Dislike vote (p. 141). Pinterest connection and Airbnb referral/contact-import screens show possible actions, not user authorization to perform them (pp. 142–143).

## Content management needs state, persistence and recovery

Original content-management examples were inspected through p. 191. The opening gallery shows: Airbnb wishlist status, Gmail star, Facebook favorites menu, Medium bookmarked list and Twitter profile counts (pp. 145–148). The common star/heart/list imagery does not establish identical audience or persistence.

Favorites/bookmarks support intentional return, while a public like or automatic history can expose different information (pp. 145–147). State actual visibility rather than assuming every product's star is private. Dashboard counts need definitions, context and useful next decisions; followers/volume do not measure task success (pp. 148–150). Viewport-triggered playback is not proof of intention, even in a video feed; resource and user-control implications remain (pp. 151–152).

Hover controls and right-click/selection menus can offer contextual actions, but need access that fits other inputs and an understandable current target (pp. 153–158). A visually clean screenshot does not prove discoverability. WYSIWYG can expose formatting without markup, but the preview still needs to represent the actual output and support input/recovery (pp. 159–160). It is not a universal substitute for plain text or required for a simple chat composer.

Autosave should describe actual persistence, pending/failure/retry and recovery boundaries (pp. 161–162). Reject the claim that it prevents all data loss or that named products implement it flawlessly. A “Save” control needs real behavior rather than merely a feeling of control. Frequent local saves, server persistence and delivered messages are different states.

Lightboxes and reduced-chrome/fullscreen views are optional task-focused alternatives, not essential for every gallery (pp. 163–166). Preserve a clear exit, task position and relevant input/focus behavior. A dimmed background does not itself guarantee preserved position or performance. Distinguish a full-viewport layout from browser/OS fullscreen.

Map/list correspondence and automatic search after moving a map can support spatial comparison (pp. 167–170), but are not inherently augmented reality or always clearer than a list. Define what triggers a query, what changed, and a usable non-map route when needed. A map background is inappropriate where location adds no useful information. Grouping friends/content, grids, cards and lists are organization alternatives rather than mandatory visual styles (pp. 171–179). Retain meaning/order and task continuity across views.

Hidden secondary information needs a perceivable trigger/state; a colored bar alone is not sufficient to explain extra tags (pp. 180–181). An empty state can explain an initial absence and next useful action, but missing results, loading, permissions and errors are distinct conditions (pp. 182–184). Clearly label examples instead of inventing real messages/data. Direct editing still needs discoverable entry, save/cancel semantics and recovery; the source's own examples include edit modes despite its no-mode framing (pp. 185–186). Dragging/reordering requires a known target, insertion/destination feedback and a usable alternative, not animation alone (pp. 187–188).

The closing reaffirms contextual adaptation and no universal solution (pp. 189–190). The inspected p. 191 is a UXPin promotional back cover listing libraries, fidelity, interactions and responsive capabilities; these are historical vendor claims, not verified functionality. Reused examples across the library do not establish independent research evidence or current product behavior.

### Content-gallery observations

- Quora/LinkedIn profile metrics and Medium's network statistics (pp. 149–150) give counts/series, not a definition of meaningful success. The Medium image includes a zero-valued chart and a no-published-posts message; these need not imply a service failure.
- Facebook/Vine feeds and Pinterest/Facebook/Stack Overflow/Pocket contextual-control examples (pp. 151–155) show visible surfaces. No autoplay, hover access, keyboard or delivery behavior was exercised.
- Drive/Dropbox object menus, Medium text-selection tools and Quora's Embed Quote trigger (pp. 156–158) identify the current target differently. Gmail formatting and Medium's selected-text toolbar (pp. 159–160) need not be copied into a plain-message composer.
- Gmail's draft and Medium's **Saving...** header (pp. 161–162) visibly distinguish editing/pending from completed persistence. The claim of a draft that autosaves is not evidence that this particular save finished or survived an interruption.
- Facebook/Pinterest lightboxes (pp. 163–164) retain surrounding context visually. YouTube's full-screen image explicitly offers Escape, whereas Medium's minimal editor still shows browser chrome (pp. 165–166); viewport reduction and browser fullscreen are different modes.
- Airbnb/Yelp/Foursquare map/list examples (pp. 167–170) connect result selection with map position. Yelp explicitly shows a redo-search-on-map-move checkbox; automatic query behavior is a product decision, not an unavoidable property of maps.
- Google+ circles, Facebook relationship lists, Google Music playlist menus and eBay collection creation (pp. 171–173) mix grouping, sorting and publication. The eBay dialog includes a public-collection notice; do not describe every grouping as private or every drag as reordering.
- Pocket/Pinterest/NYTimes/Digg grids (pp. 174–176) have different item heights, media and grouping. Twitter/Asana/Pinterest/Google+ cards (pp. 177–179) likewise serve posts, task detail or browsing; a task list/detail image is not proof that every item needs a card border.
- Medium's inline note count reveals a comment panel (pp. 180–181); the trigger must communicate its purpose. Airbnb's illustrated sample, Pinterest onboarding, Tumblr's new dashboard and Spotify's empty saved songs (pp. 182–184) give different first-use prompts. Spotify still displays a player beside an empty library: one empty region does not imply the entire app is empty.
- Asana's inline task field and Medium's explicit Cancel/Save controls (pp. 185–186) demonstrate that direct editing can still have an edit state. Asana's dragged item and Google Music's queue (pp. 187–188) visually suggest movement without establishing actual accessible reordering or persistence.

## Application status

For both modes, retrieve patterns by the actual task, input method, states and consequence, not a familiar screenshot. Proposed chatbot recovery and game-page actions need explicit implementations and checks. Neither a screenshot nor the full reading establishes implemented, accessible or effective behavior in either demo.
