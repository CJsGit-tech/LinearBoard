# W02 — Responsive Web Design Best Practices

**Source:** UXPin, 2015; Ben Gremillion, Jerry Cao and Zack Rutherford (p. 6). Exact filename: `Web Design/Responsive Web Design Best Practices.pdf`. All PDF text pp. 1–127 read, 123 original pages inspected. Body folios match PDF pages; contents-list entries near the last chapter are offset, so use PDF locators. All original screenshots, charts and tutorials reviewed; no historical service, tutorial tool, conversion experiment or device interaction was executed.

## Start with purpose and content

Fluid layouts, flexible imagery and conditional styling support adaptation, but do not guarantee accessible, consistent, cheaper, future-proof or commercially successful experiences (pp. 7–22). Retain content inventory, task priorities, meaningful labels, realistic content extremes and adaptation beyond a handful of screenshots (pp. 23–38, 112–126). Narrower content may require greater height; that does not mean physical screen height must be proportional to width (pp. 20–22).

The opening business figures and 2020 forecast are historical. A 79%→59% change is 20 percentage points, not a 20% relative decrease (p. 13). Plusnet also increased marketing spending; attributing the reported results to the “single act” of responsive design contradicts the source's own caveat (pp. 15–16). The 11%, 40%, tenfold and Time figures are neither isolated causal evidence nor forecasts here. The automatic SEO boost claim is not adopted or verified as current search guidance (pp. 12–16).

Prioritize intersecting user/business goals, including what a person receives for providing an email (pp. 23–25). Do not equate responsive design with behavioral personalization, collect history/location by default, or infer permission from a device capability (pp. 25, 31–38). A food-service tagline does not establish that GPS is essential; manual location entry may serve the task. A small viewport does not justify automatically shrinking localized text, imposing a specific navigation location or removing necessary repeated access (pp. 25–28).

No fixed three-to-five-view count, mandatory minimalist bank, rectangular-card guarantee, compulsory infinite scroll or one-page-per-category rule follows from content-first (pp. 26–31). In the actual Simple example, the email action says Get Simple; it does not illustrate the sole login described in the prose (p. 28). Virgin's screenshots show stacked trip fields, a city selection surface and dates, but do not establish instant speed, no network requests, calm from color or increased bookings (pp. 34–37).

## Adapt layout and navigation meaningfully

Mostly fluid, column drop, layout shifter, tiny tweaks and off-canvas are useful candidate arrangements, not an exhaustive taxonomy or fixed breakpoint count (pp. 39–43). Preserve a meaningful reading/focus sequence when repositioning content. Changing the navigation's presentation can preserve labels and destination meaning; neither every style nor every dimension has to remain identical (pp. 44–65).

Useful guidance: adequate actual targets, separation to avoid mistaken activation, alternatives to hover, prompt truthful feedback, explicit menu labels where recognition is uncertain, and search where the content/task warrants it (pp. 45–53). Do not adopt a universal lower-left phone/upper-corner tablet placement, 44-point web target, 23-point gap, five-user proof threshold, mandatory search, or compulsory haptic/animation response. Screen width does not identify available inputs. Essential links should not be withheld merely because the destination's mobile layout is imperfect.

A shrinking persistent bar trades visible access against content space; footer anchors trade compactness against travel; drawers trade space against discoverability; narrative content can offer exploration alongside direct destinations (pp. 54–65). The p. 56 heading/prose confuse header and footer: the illustrated Contents example uses Explore to reach footer navigation, not one unambiguous universal anchor pattern. Test actual destinations and focus.

The UXPin drawer tutorial illustrates grouping, an off-canvas surface, activation, movement and return states (pp. 66–77). Its hidden hotspot/nested-animation workaround, easing, -200/320px positions, sharing steps and ten-minute claim are historical tool instructions, not reusable implementation requirements. A drawer needs explicit usable open/close and keyboard/focus behavior; reproducing motion alone does not establish that. Swiping is optional, not the sole access/recovery path.

## Type and units need correction

Retain testing actual font, measure, line rhythm, content and user context rather than assuming device width reveals reading distance (pp. 78–87). No mandatory 1.6× headline, 14pt mobile reduction, 45–85-character range across every script, 60-character line or two-word/5rem action follows. Longer wording does not alone determine an activation region. A heading can be distinguished through more than size.

The original p. 83 table mixes points/rem with viewport pixels, and p. 84 calls 140% of a 1rem base 1.3rem; these are source errors visible in the originals. For a 14pt root, 320 CSS px is about 17.14rem, not 22.9rem; for 16pt, 960px is 45rem, not 60rem. A 1rem base ×1.4 is 1.4rem. [MDN length definitions, checked 2026-10-25](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length): CSS px and device pixels differ; 1pt = 1/72in and 1px = 1/96in. `em` uses the element's font size except on `font-size`, where it uses the inherited size; `rem` uses the root size. Neither inherently scales with viewport width. Relative units can also serve layout; the source's ban on structural ems is not adopted.

The p. 26 maximum-scale=2 recommendation conflicts with p. 32's user-control emphasis. [W3C Resize Text, checked 2026-10-25](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) requires text resizing through 200% without content/function loss, with specified exceptions; 200% is not an instruction to cap zoom. Check intermediate zoom steps and responsive variations as applicable. See also the separate [reflow reference](../current-accessibility.md#reflow).

## Images, code and performance need verification

Plan useful imagery and resource cost, inspect content at intended sizes, and choose an encoding appropriate to the image (pp. 88–102). Distinguish codec quality settings from compression amount: the source reverses that terminology and its 20–70 recipe is not a universal encoder setting (pp. 89, 94–96). Eliminating source colors changes the image; “visually similar” does not prove identical data or no quality loss (p. 94). The PNG chart p. 97 has inconsistent axis labels and does not establish one optimum color count.

The claim PNG-24 has no compression, simplified opacity split, and p. 110 attribution of LZW to PNG are inaccurate. Focused checks **2026-10-25**: [MDN PNG section](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types#png_portable_network_graphics) describes lossless compression and alpha; [W3C PNG Third Edition §10](https://www.w3.org/TR/png-3/#10Compression) specifies deflate/zlib. Color quantization before encoding is distinct from that lossless encoding. Only these relevant external sections were reviewed, not the full specification.

The `<picture>` snippet p. 100 puts alt on the wrong element, source elements after img, and describes media as container width. [MDN picture documentation, checked 2026-10-25](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/picture) describes source alternatives before the img, with alt on img; selection supports art direction/format choices, and img srcset can offer density alternatives. The book's “experimental/future” status is historical. CSS display scaling alone does not establish a smaller download.

The p. 105 diagram sets gray #444, despite the prose saying red. The p. 106 query uses `(color: true)` and its explanation inserts an absent exactly-320px condition alongside min-width:480px. [MDN color media feature, checked 2026-10-25](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/color) uses integer bits per component or boolean `(color)`. [MDN orientation, checked same date](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/orientation) concerns viewport proportions, not physical rotation; a soft keyboard can alter those proportions. Do not infer screen-reader exclusion from `screen` media or universal 2× density from “high resolution.”

Retain measuring relevant load/interaction costs and preserving maintainable source while producing appropriate delivery assets (pp. 103–111). Do not mechanically strip all HTML/JS whitespace, equate gzip with a downloadable ZIP, assume every request has a fixed serial delay, or always bundle every asset. No performance benchmark was run here; resource advice and named tools must fit the current project and delivery behavior.

## Application

For the Web game page, adapt imagery, release details and primary action without hiding required information. For mobile-web chat, test navigation, readable turns, long content, keyboard-height changes and preserved drafts/state. These are design-pro applications; desktop resizing is not physical-device, native-runtime or user evidence.
