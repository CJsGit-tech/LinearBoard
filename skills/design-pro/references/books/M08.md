# M08 — Tablet Web Design Best Practices

**Source:** Mobify, *30 Ways to Create Amazing Web Experiences on Tablets*. Original filename: `Mobile Design/Tablet Web Design Best Practices.pdf`. PDF pages are used below; most visible folios match them. The introduction discusses 2013/2014 shipments and examples include Google+, Nexus tablets and early browser APIs. No precise publication date is established. This historical vendor guide divides incremental adaptation (pp. 7–15) from tablet-specific enhancements (pp. 17–24).

## Adapt interaction, not just width

**Activation area differs from the visible icon and surrounding gap.** The diagram on p. 8 distinguishes padding, which extends a target, from margin, which separates it. This supports checking actual hit areas. Its 44×44px recommendation is a historical comfort heuristic, not a universal native or current web requirement. Read the [current web target guidance](../current-accessibility.md#target-size) for requirements and exceptions.

Reduce unnecessary keyboard entry while retaining correction. Google Flights uses suggestions after partial input (p. 9); contextual keyboards expose characters relevant to email, URL or phone entry (p. 10). Avoid autocorrection/capitalization where these would corrupt identifiers (p. 11), rather than disabling useful language assistance in every field. The code snippets are historical examples, not implementation guidance verified for today's browsers.

Do not make essential information or actions available only on hover. The lululemon example sends touch users to the full product page instead of relying on desktop quick-view hover (p. 13). Design-pro synthesis: preserve the task through touch, mouse and keyboard; an alternate route can differ from the hover presentation without removing useful content.

## Reading, layout and assets

- Choose readable type and line spacing; the source's 16px and 1.5 suggestions explicitly allow contextual adjustment (p. 11). Do not treat a CSS size alone as proof of readability.
- Use flexible content widths and evaluate portrait and landscape. The Tommy Bahama example changes navigation visibility with available room (pp. 13–14); it does not justify inferring user intent from orientation alone.
- Provide suitable image detail without sacrificing performance; keep meaningful text outside raster images (pp. 12, 15). The claim that icon fonts are always best (p. 12) is dated. Check the existing asset system, semantics and rendering before choosing a format.
- Treat performance as part of task completion, including image cost and loading (p. 15). Its specific abandonment percentage and suggested build tools are historical; neither one image-size threshold nor universal concatenation advice follows from it.
- Test representative devices and conditions (p. 15). The listed iPad/Nexus/Surface models are examples from the period, not a current coverage matrix.

## Progressive enhancement and navigation

The second part starts with useful core content and enhances for device/context (p. 17). It then proposes sticky navigation (p. 18), contextual teaching (p. 19), adjustable reading size and related-content carousels (p. 20), side panels and transitions (p. 21), home-screen treatment (p. 22), reach-oriented actions (p. 23) and large imagery (p. 24).

Use these as options. The Google News arrow specifically signals additional content before a first swipe (p. 19). The Mashable edge panel illustrates secondary navigation (p. 21), not permission to hide every primary action. Sticky navigation should not occlude content; panels need understandable opening, closing and focus behavior; animation should communicate rather than decorate. These qualifications are design-pro synthesis.

The lower-corner reach map (p. 23) assumes a particular two-handed hold. Check the actual grip, stand, keyboard and assistive input. A tablet is not necessarily handheld or used in a different setting from a laptop. Avoid a separate codebase or complete navigation replacement solely because the source's sales narrative favors bespoke tablet experiences.

## Rejected and dated guidance

**Do not copy the instruction to disable page pinch-to-zoom (p. 18).** A layout that its author finds readable does not remove a user's need for magnification. This prescription also conflicts with the adjustable-font-size guidance on p. 20. Preserve user enlargement and test layout adaptation rather than locking scale.

Location-based shipping estimates (p. 19) are optional assistance, not an excuse to require geolocation. Provide a manually correctable route; location does not necessarily identify a shipping address. Camera capture, URL-bar hiding and app-capable metadata snippets (pp. 14, 22) describe old platform behavior; do not promise them without current verification. Native-looking transitions or hidden browser chrome do not establish native capability.

Conversion, spending and navigation-speed percentages (pp. 5, 12, 15, 18) are historical promotional claims without sufficient methodology here for design-pro benchmarks. Repeated lines in extracted pp. 1, 19, 20 and 22 come from the PDF's layered content; visual review shows one intended layout, not multiple distinct recommendations.

## Demo applications

For the game page, preserve readable release information in either orientation and provide an explicit route to gameplay content. For mobile web chat, use a real editable composer, retain zoom, test layout with long content and distinguish a narrow desktop viewport from a physical tablet/phone keyboard test. These are applications of the interaction and verification principles, not claims that the book supplies a chatbot specification.
