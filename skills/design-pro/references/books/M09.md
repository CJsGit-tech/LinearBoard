# M09 — Enterprise Commerce Progressive Web Apps

**Source:** Mobify, *The Enterprise Guide to Delivering Commerce Progressive Web Apps*. Original filename: `Mobile Design/The Enterprise Guide to Delivering Commerce Progressive Web Apps.pdf`. Locators are PDF pages. The text anticipates adoption in 2019 (p. 3) and cites Gartner's 2017/2018 architecture material (p. 4); it does not establish an exact publication date. This is a vendor's enterprise architecture argument, not a complete UI or current PWA implementation manual.

## Transferable decisions

**Inspect the existing delivery system before prescribing a front end.** The guide compares commerce-led, CMS/experience-led and API-led approaches (pp. 4–9). The diagrams distinguish which layer owns the experience and whether mobile/tablet work introduces a second front end. Useful questions include where content and commerce data originate, who can change UX, what a deployment touches, and whether multiple codebases create maintenance cost. Do not require decoupling for every design task.

**Assess change and ownership costs together.** A quickly added mobile front end may improve a high-priority channel but duplicate maintenance (pp. 5–6). An API layer can separate release concerns, with time-to-market and integration work still needing assessment (pp. 7–9). The promise of permanent future-proofing is too strong: changing data contracts, identity, business rules and service reliability can still affect the experience. This qualification is design-pro synthesis.

**Evaluate the whole task, including performance.** The product-list example defers some items instead of downloading everything before use (p. 8); later sections discuss initial-load cost, rendering, code splitting and integration/event quality (pp. 10–14). These are options to measure against actual content and user journeys, not a rule that every page needs infinite scroll or a single-page application. The source does not evaluate focus, orientation or access to the footer under endless loading.

**Make operating responsibility explicit.** Its custom-front-end discussion includes testing, monitoring, deployment, caching, global delivery and maintaining integrations (pp. 10–12). A reference storefront still requires work to become a useful product; visual polish and task usability are not supplied automatically by example code. The comparison sheets (pp. 16–17) suggest useful evaluation dimensions—experience, integration and operations—but their ratings are vendor assertions.

**Explain tradeoffs in the audience's terms.** The stakeholder appendix separates concerns of technology, ecommerce and marketing teams (p. 18). Use this to surface constraints and responsibilities during discovery, without promising everyone the same revenue or agility benefit. A small local prototype need not acquire enterprise infrastructure merely to demonstrate its UI.

## Architecture diagrams and limitations

The pp. 4–7 diagrams show a move from platform-owned presentation toward a shared customer-facing layer above commerce and CMS. The p. 13 stack explicitly inserts Mobify between device experiences and backend/integration systems. This shows the proposed integration position, not evidence that an equivalent architecture is mandatory or fastest.

The source favors Front-end as a Service and its own platform, while describing custom and vertically integrated alternatives unfavorably (pp. 10–17). Do not reuse its provider rankings, deployment counts, 18–24-month build estimate, 3–4× speed claim or guaranteed revenue gains as current comparative facts. It supplies no controlled comparison demonstrating them. A single codebase also does not guarantee equivalent usability across touch, keyboard and assistive input.

The claim that a PWA must look native or requires a fundamentally different design from responsive web (p. 10) is a quoted design opinion. It does not define PWA capability, prove accessibility or justify discarding existing web patterns. AMP, app-store wrapping, platform exclusivity and named product capabilities are historical claims requiring current primary-source verification before implementation. No such services are necessary for the two demos.

## Scope for design-pro

Use this book mainly for architecture-aware discovery, maintainability and performance tradeoffs. It provides little direct support for mobile spacing, form-error placement or native platform conventions; do not cite it to invent those answers. For the demos, inspect the available stack, implement only the needed interaction and label simulated behavior honestly.
