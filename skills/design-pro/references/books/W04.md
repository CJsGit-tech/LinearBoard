# W04 — The Enterprise Guide to Headless Commerce Front-ends

**Source:** Mobify, undated vendor guide; p. 14 reports 2018 activity and projects 2019, establishing its historical context rather than a verified publication date. Exact filename: `Web Design/The Enterprise Guide to Headless Commerce Front-ends.pdf`. PDF text and all 14 originals reviewed; printed body numbers match PDF pages. This is architecture/product marketing, not an independent UX comparison. The cited Gartner figure is reproduced in the guide; the underlying Gartner report was not separately reviewed.

## Retained questions and tradeoffs

The three models distinguish a front-end built within a commerce platform, within a CMS/DXP, or drawing capabilities through APIs (p. 4). The useful design question is which constraints actually stop the team from delivering a needed experience. Inventory existing platforms, component reuse, content ownership, integrations, release practices and user tasks before choosing a model. A visual redesign does not itself require architectural replacement.

Separating a presentation layer from backend systems can permit some independent changes, but introduces contracts and dependencies that must still work together (pp. 5–10). The original diagram p. 6 shows multiple channels coupled to commerce, CMS, analytics and personalization. Pp. 7–8 replace this with a common service layer and depict backend replacement beneath retained front-end channels. These are proposed dependency models, not proof that every front-end can remain unchanged through a backend migration. Data semantics, error handling, authentication, performance and integration behavior still need assessment; this is design-pro synthesis.

The custom-build discussion identifies real work to consider: development/testing, delivery, hosting, caching, scaling, monitoring, security maintenance and integration changes (pp. 8–10). The p. 9 diagram emphasizes duplicated connections across channels; the p. 10 alternative draws one branded layer. Compare total ownership and actual contracts rather than treating the more orderly picture as measured simplicity. Existing components, libraries or managed capabilities may reduce custom work; the source's all-from-scratch framing is too narrow.

The vendor proposal groups delivery network, developer tooling and integration architecture (pp. 10–12). For a genuine choice, examine maintainability, supported interactions, observability, data/control boundaries, exit cost, release responsibilities and fit with the team's skills. Offloading operations changes responsibilities; it does not eliminate them. These evaluation questions are synthesis, not independent results demonstrated by the source.

## Claims that are not reusable requirements

- “Only” API-led architecture can deliver good experience, all coupled systems require rebuilding every 3–5 years, all UX changes require heavy redeployment, and headless always requires custom hosting are unsupported universal claims (pp. 2, 5–9).
- Headless does not guarantee speed, accessibility, security, higher conversion/SEO, brand loyalty, future-proofing or freedom from future rewrites (pp. 2–3, 6–8, 12–13). Architecture and customer outcomes need separate evidence.
- PWA/AMP as the latest obligatory technology and the depicted single-codebase/native capability are historical claims about an offering, not present requirements (pp. 9–12). No current vendor availability, feature set or browser/platform support was verified here; none is recommended from this guide.
- The once-monthly versus five-monthly deployment comparison lacks a comparable sample or method; deployments are not automatically successful UX changes (p. 11). Testimonials, market leadership, integrations, GMV and the 2019 forecast are vendor statements, not causal evidence or current facts (pp. 12–14).
- Routing all shopper events to marketing systems is not a default design obligation; determine useful data, permission and user expectations before adding analytics (p. 12).

None shows a controlled task test, a runtime benchmark or an accessibility audit.

## Application

For Web Apps, gather architecture constraints when they materially affect a journey, then design recoverable loading/error states and realistic capabilities. Mobile may share data/contracts while retaining platform-specific interaction behavior. The local game page and mobile-web chatbot demos need neither commerce replatforming nor this service. Scope-appropriate local simulation is sufficient. This is design-pro application, not a commercial result from the guide.
