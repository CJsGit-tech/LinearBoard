# P01 — Building UI Mockups Developers Won't Hate

**Source:** Jerry Cao and Jake Rocheleau (author profiles p. 5; signed introduction p. 7), UXPin, copyright 2015 (p. 3). Exact filename: `Wireframes, Mockups, Prototypes/Building UI Mockups Developers Won't Hate.pdf`. PDF text pp. 1–34 read and all 34 originals inspected, including covers and image-only closing promotion. Printed body folios match PDF pages. This is a historical collaboration/asset-handoff guide with vendor examples, not a controlled study or current tool-support matrix.

## Shared understanding and feasibility

Pp. 6–11 treat mockups as material for ongoing collaboration rather than a finished picture thrown over a wall. A designer should understand enough of the medium to discuss inputs, rendering, styling, responsive changes and state behavior (pp. 8–10). Practical decomposition can clarify a component's role and dependencies, but Atomic Design's five tiers are not mandatory architecture. The LEGO photo p. 11 is an analogy for composition, not evidence that every developer can reconstruct any interface from a live example or that all examples improve retention. A developer/designer can be the same person; do not impose occupational stereotypes or a requirement to avoid learning code.

Pp. 12–14 suggest reviewing constraints before investing in polished interactions. Keep known obstacles, alternative approaches and the user impact of each compromise visible. A weekly review is a possible cadence, not required for every task. Prototyping can expose missing transitions or browser chrome collisions, but a prototype using a different runtime may not reproduce those problems. The colored four-step rectangles p. 12 and clickable-wireframe editor p. 14 illustrate structure and configuring a trigger, not tested feasibility. The p. 14 suggestion to substitute cards for infinite scroll mixes independent decisions: a card collection can itself use infinite loading. Define layout and loading/navigation separately.

## Platform and support boundaries

Pp. 15–17 distinguish native apps from browser-delivered interfaces. Preserve that distinction, but do not reduce native variation to a single OS plus resolution; actual OS versions, input/accessibility settings, windowing, keyboards and hardware can matter. Likewise a successful desktop web preview does not validate a physical mobile keyboard. The colored responsive chart p. 15 is an illustrative cheatsheet, not evidence of required breakpoint values.

The libraries, CSS support statements, Flash fallback, IE6–8 shims and mobile-detection snippets are historical recommendations (pp. 16–17). They were read, but no current support/maintenance/license check was performed and none is recommended or installed by this note. Do not assume a compatibility library supplies every missing capability, that a player supports every format, or that device detection establishes user needs. Define the actual support environment and essential baseline; research an authoritative current capability only when needed for implementation. Prefer existing capabilities before adding dependencies.

## Pages, components and state coverage

Pp. 18–20 correctly extend attention beyond the homepage. The sitemap p. 18 separates About/Work/Blog/Contact descendants and footer destinations; these are examples, not mandatory sections. Homepage effort need not dominate an app whose main tasks are elsewhere. P. 19 allows representative mockups for similar pages, then says separate pages are safest even when only icons differ. Resolve that tension through a shared component/variant contract and representative states rather than automatically duplicating every page. An icon change may or may not require its own design review.

P. 20's checklist usefully calls for open/closed interaction states, relevant signed-in/out states, labels, error/success content, assets and notes attached to the affected section. Specify only states the product actually has; this does not authorize adding accounts, loaders, error-page photography or animated media. P. 19's folder/upload/download/settings icons do not establish universal recognition. The p. 20 annotated search mockup demonstrates location-linked discussion; a comment referring to research is not the research itself or proof that whitespace produced an outcome. A recorded state and a runnable transition support different checks, and duplicate documentation can drift.

For chat, define message/draft identity and pending/success/failure/retry transitions, including whether navigation interrupts them. For a game page, define where the main action leads and what a local simulated result means. These are design-pro applications of explicit states and resources, not completed project tests.

## Responsive behavior between pictures

Pp. 21–23 ask useful questions about logo/image size, text/line height, navigation and secondary columns/footer content. The p. 21 prototype editor shows named presets (320, 480, 600, 768, 992, 1024 and 1224px) plus Custom; those are historical tool options, not universal device widths or required layout changes. P. 22's expanding grid illustrates a concept without proving reflow.

Record representative narrow/wide states, rules for intermediate widths, content extremes and relevant orientation/zoom behavior. More screenshots cannot cover every possible situation, and developers still need judgment (contrary to p. 23). Missing/hidden essential content is not equally acceptable merely because p. 22 says there are no wrong answers. Mobile-first can reveal content priorities; it does not guarantee an enjoyable device-agnostic experience or apply to every existing-product change. Label the meaning of any dimensions, state, revision and delivery scale rather than imposing one filename format or conflating pixels with physical device density.

## Assets, realistic content and change history

Pp. 24–28 emphasize findable resources, meaningful names, real text, font identities, colors, layer groups, asset exports and interactive examples. Retain enough context that another implementer can find the right version and connect it to a specific component/state. Preserve existing tokens and assets rather than re-exporting every element as a bitmap or copying isolated hex values that diverge from the product. Sizes should describe use/crop/scale; a responsive asset need not have only one fixed display size (p. 20). A font file's inclusion requires actual applicable rights, not simply that the file is available. No particular asset license is determined here.

The p. 27 figure shows a person moving between two boxes and returning; it is a simple process analogy. P. 28's file browser with UI-kit revisions is not a version-history guarantee. Version control can support comparing/restoring design decisions, but the systems/services and claims about PSD previews, GitHub being open source/public by default, PixelNovel ownership, Pixelapse availability and one-click history are not adopted as current facts (pp. 28–30). Check the project's actual storage/access/history rather than infer privacy from a brand name or subscription claim. P. 30's Save current state as iteration dialog also includes comment-copy options; the screenshot alone does not establish backup, retention, collaboration or successful save/reload.

Tool/plugin lists pp. 31–32 and closing vendor claims p. 34 are historical, not requirements. Exported CSS or measured coordinates do not establish semantic HTML, focus, keyboard access, responsiveness or production behavior. P. 33's suggestion that designers finish before developers take over conflicts with the collaborative premise; keep a feedback route during implementation. Clarify consequential uncertainty without producing exhaustive duplicated artifacts or treating over-explanation as always beneficial.

## Assessment and applicability

Both modes benefit from a shared behavior/asset contract, realistic content and feasibility checks. Web needs actual browser/input/reflow checks; native Mobile requires its own runtime/platform checks; mobile web remains browser-delivered. A static mockup, interactive simulation, code review and executed task each establish different things. This note records full source review, not an actual team collaboration session, browser test, native run or user study. See [prototype and evidence distinctions](../concepts/prototyping.md).
