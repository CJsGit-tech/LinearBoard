# P07 — The Woork Handbook

**Source:** Antonio Lupetti, version 0.1; cover says January 2008, but introduction refers to January–December 2008 and some article links say January 2009. Preserve this internal date inconsistency rather than invent a publication date. Exact filename: `Wireframes, Mockups, Prototypes/The Woork Handbook.pdf`. PDF pp. 1–133 fully read and all 133 original pages visually inspected, including diagrams, screenshots, code and font specimens. Printed body folios match PDF positions. Extraction emitted object-pointer warnings for objects 23/1130, with no page exceptions; originals were used to check visual material. Linked scripts, APIs, tutorials and vendor services were not executed. This is primarily historical Web implementation instruction; transferable design ideas also apply to mobile web, not current native APIs.

## Maintainable structure and meaningful roles

Pp. 5–13 discuss CSS organization, draft structure, readable grouping and incremental browser inspection. Choose file boundaries by actual complexity and existing architecture; a single file, alphabetical properties, tabs, a table of contents or a particular reset are preferences rather than universal requirements. A manually numbered contents list has maintenance cost (pp. 6–7). Avoid unnecessary wrappers, but the six-versus-two example and four–six-section suggestion (pp. 9, 20) are not element quotas. Necessary structure and accessible semantics can justify extra markup.

Pp. 14–17 contrast positional names with stable content roles. The original p. 14 diagrams swap main/sidebar positions, retaining semantic names while positional names become misleading. P. 15's heading/paragraph example supports meaningful markup; a class named main does not itself supply HTML semantics. Follow the project's established naming and component patterns, including useful utilities; the book itself adds color/position utility classes on p. 13. It inconsistently asks for lowercase and permits camelCase. Neither an always-horizontal navbar, seven-region layout, nor treating logo/copyright as the whole header/footer is mandatory.

The example `.container` width of 855px (p. 11) cannot automatically resize fixed-width children 472px and 353px plus a 30px margin, despite the prose. CSS `column-left` differs from HTML `column_left` (pp. 11–12). Pp. 17–20's fixed 780px three-column blog and 120×600 ad slot are historical samples, not responsive design specifications. Original p. 18's diagram mixes hyphen/underscore naming too. P. 19 has a missing selector comma and `heigth` typo. Pp. 20–24's top-down organization can clarify regions, but reducing class count is not sufficient for maintainability; broad tag rules may leak. A CSS-background logo with a separate Home link does not establish equivalent usability or an accessible brand name (p. 22). P. 23 visually labels post text as h2, while prose/code assign h2 to the date; neither typographic size nor sample tag choice establishes a meaningful heading structure.

## Pagination, forms and disclosure states

Pp. 24–28 distinguish current page, available pages and enabled/disabled previous/next. Preserve that state distinction, not the Flickr/Digg branding, 11px text, tiny targets or float-based implementation. Original p. 27 places the Digg-style result after p. 26's introduction. Its CSS contains missing semicolons. Styling a list does not supply navigation labels, current-page semantics or keyboard/focus verification.

Pp. 28–34 compare form layout approaches. P. 29's nested label/input can associate them implicitly; the footnote's dismissal as a semantic hack is not adopted. Conversely, p. 32's separate labels have no `for` association and its password field uses `type="text"`. The original diagram shows label/helper/input alignment, not accessible operation. Persistent readable labels and useful helper text are the transferable ideas. Do not copy right-aligned fixed 140px labels, a 400px form, a six-character password policy, or an anchor with `onclick` as a substitute for a submit button (pp. 30–34). Table layout preference p. 31 is not a reason to encode form layout as tabular data. Numeric dimensions and colors are tutorial values, not standards.

Pp. 34–41 use nested image backgrounds for rounded containers, expandable sections and fluid input decoration. Original pp. 35, 37 and 40 identify each decorative edge. Retain separation of content and presentation; do not require four nested wrappers or bitmap corners for a new interface. P. 39's display toggle has no expanded-state announcement or focus policy; a styling effect is not a complete disclosure contract. P. 40's label/input separation again lacks explicit associations. A 100% input plus extra padding requires actual sizing/overflow inspection, not a claim that liquid width guarantees adaptation.

Pp. 41–48 show default/current/hover navigation states with text-sized widths. The original sprite p. 42 and code p. 44 reverse the prose's standard/hover background offsets. These are destination links called tabs, not necessarily an in-page tab widget requiring tab roles. Preserve the active destination and visible focus, not an image-sprite recipe. Pp. 48–50 explain URL-driven content routes using fixed allowlisted includes; this is useful traceability between selected link and displayed content, not a universal routing architecture. The printed example has extra/mismatched braces; it was not run.

Pp. 51–55's login/register disclosure distinguishes a registration destination from form submission. Original p. 51 annotates a link for Register and a button for Log-in. P. 52 correctly connects email/password labels, but again uses text for the password and omits names for submitted inputs; the fixed-size overlay lacks a demonstrated focus, dismissal or error contract. Plain JavaScript may be sufficient for a small toggle (p. 55); do not add a framework merely for a visual effect. Reuse an existing accessible component when available.

## Historical mobile-web proposal

Pp. 55–59 suggest a separate mobile path/subdomain, optional device redirects and a single-column layout. The durable idea is readable prioritized content and avoiding irrelevant heavy widgets, not compulsory separation or user-agent routing. Do not remove useful features merely because someone uses a phone. The sample 12px text, 14px headings, 11px footer, low-emphasis gray links and absent image alternative are not a modern accessibility prescription. The selector `h1 a:link, a:visited` also affects visited links outside h1. The Windows Mobile font-copy workaround and WordPress plugin recommendation are historical, unverified-current instructions; choose available fonts/fallbacks without requiring visitors to install a font. Browser mobile layout does not establish native mobile navigation or physical-keyboard behavior.

## Data relationships and consequences

Pp. 60–69 cover user/site/share and user/city entities, attributes, cardinality and foreign keys. Original pp. 62–65 show a junction joining two one-to-many relationships; p. 67 connects a user's city ID to the city record. **Design-pro application:** understand which records/actions are related before designing edit/delete consequences. A relationship represents actual memberships, not literally every possible Cartesian combination as p. 62 suggests. A count of shares requires a consistency policy; a diagram alone supplies none.

Do not adopt the SQL/PHP as production code. Pp. 63/66 contain `DATA`, an incomplete primary key and old engine syntax; p. 69 omits a comma. Password columns of length 20 demonstrate no safe credential handling. Integer keys are not universally required, and cascading deletes are one consequential policy, not the definition of referential integrity. Original phpMyAdmin screenshot p. 68 shows an old UI and available fields, not proof the intended city relationship was saved. Pp. 65–66's runnable database-creation file under site root is not an authorized deployment/migration workflow. No database was created or modified during this review.

## Asynchronous feedback without false success

Pp. 70–85 cover request creation, cache workaround, insertion, inline editing, deletion and search. Retain the conceptual separation between input, pending feedback, server result and displayed outcome. ActiveX/browser-name detection and random query parameters are historical implementation choices, not current compatibility or caching requirements.

Pp. 73–74 and 76–77 display “Site added” whenever readyState reaches 4, without checking transport or application success. Error text could therefore be prefixed with success. Presence checks do not reject empty values, despite the prose. Raw SQL interpolation, unescaped HTML responses, GET writes and exposed database errors are visible omissions, not a safe implementation recipe. Encoding a URL is not input validation or HTML escaping. The ColdFusion code also has malformed tags/query syntax (p. 77).

The inline-edit example pp. 78–80 looks up literal `textId` rather than its parameter, confuses ID and value, and INSERTs rather than demonstrating an existing record update. P. 80's isset test does not establish the claimed blank-input rejection. Deletion pp. 81–82 duplicates an example user ID, serializes an element absent from the shown markup, and has no demonstrated authorization, confirmed server result, recovery or visual reconciliation. Use these as reasons to specify complete affected-record state, not to copy code.

Search pp. 83–85 supports explicit and while-typing entry, but has mismatched parameter names (`name` versus `searchq`), mismatched query variables, malformed output and no shown stale-response, failure, empty-result or cancellation handling. A shared global request is not evidence of safe concurrent operation. **Design-pro synthesis:** associate results/errors with the active input or conversation and guard late results; completion of transport is not completion of the task. No claim is made that these historical snippets work.

## Effects, input limits and ordering

Pp. 86–91 introduce DOM lookup, styling and separating listeners from markup. Those organization ideas can support maintainability without requiring MooTools or treating a modern framework's declarative event convention as automatically inferior. Several code samples lack separators. Original p. 90's alert only illustrates chosen identity, not user-task usefulness.

Pp. 92–94 and the duplicated pp. 104–107 animate vertical menus; pp. 101–104 overlap absolute-positioned panels. Original images show shifted menu items and obscured layers. Hover movement, opacity changes and one-second elasticity do not prove better navigation. Do not hide essential controls behind hover or move a target just as someone tries to select it. The menu code even selects `#container div` despite markup `#menu li`, and uses hyphenated variable names. Decorative timing is not a standard; preserve stable operation and appropriate motion preferences.

Pp. 94–96 slide a product out of view. Hiding is not database deletion; define a route to restore it if needed and handle focus after removal. Lightbox pp. 97–98 shows a larger image, description, count, previous/next and close; the static screenshot supplies no proof of keyboard handling, focus containment/return or alternative text. Use an existing suitable dialog/gallery rather than automatically installing the named old plugin.

Pp. 99–101 show a 20-character counter with warning at five remaining. These are sample limits, not Twitter's present policy or a universal composer limit. A keyup-only listener does not cover every input method, and JavaScript string length is not necessarily perceived character count. Explain an actual limit and retain input meaning; color alone should not carry the warning. P. 107 says blink but code says blind; clicking an h1 is not automatically keyboard-operable.

Pp. 108–110 serialize reordered list IDs and display a new order. A hidden input update is not durable server save. Provide non-drag operation and a clear saved/failed result when relevant; do not infer accessibility from drag working in a picture. Pp. 110–113 distinguish table header/body/footer and sortable headers. P. 111 prose calls it tfooter but code uses tfoot; p. 112 has malformed PHP property access. Expose the selected sort/direction and operable control in implementation; the source has not demonstrated those semantics or any actual Ajax request for sorting.

## Services, content and visual specimens

Pp. 114–119 add external share/vote/reaction widgets. Those counts are illustrations, not verified adoption or quality evidence. Historical script URLs, template selectors, service names and placement preferences are not current integration instructions or permissions. A third-party widget introduces behavior/data dependencies; a basic demo can communicate its goal without one. Pp. 119–120's reported two-day ad-click change and 96% internal-page share are an uncontrolled personal anecdote, not a conversion prediction or proof that ads under titles benefit visitors.

Pp. 120–122 compare Blogger/WordPress, Picasa images and favicons. Preserve checking actual rendered image quality and existing content ownership; “only creativity limits you” ignores real platform constraints. Free pricing, compression behavior, storage, platform equivalence and favicon workarounds are historical claims, not recommendations.

Pp. 123–124's Twitter API form puts a password in a PHP source variable and displays a returned status; the underlying implementation is linked but absent. Do not claim its authentication or success handling works, require credentials, post messages or equate a 140-character field with a current platform limit. Pp. 124–126 parse RSS to a list. External titles/links need appropriate treatment as untrusted content; a loop does not prove safe rendering. The purported ten-item limit increments from one and breaks at ten after output, yielding nine when enough items exist.

Pp. 126–129 show historical photo editors, cropping/exposure tools, layers, undo and export/share routes; pp. 130–131 show social-network builders. Reversible edits, familiar task tools and a clear next step are potential design patterns; screenshots cannot prove speed, professional quality, unlimited storage or no-registration/free availability. Do not import Flash requirements or vendor rankings as present advice. The book calls Splashup “Slashup” in prose; original screenshot says splashup.

Original font specimens pp. 132–133 range from script, outlined and distorted display lettering to readable serif/rounded faces. They establish visual variety, not font licensing, language coverage, web embedding, accessibility or suitability for long reading. Use expressive display lettering only where it supports the game identity; keep body copy and controls readable, with actual available fonts and appropriate fallback. No specimen is an instruction to redistribute a font.
