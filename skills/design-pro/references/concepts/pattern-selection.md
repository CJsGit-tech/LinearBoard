# Pattern selection, consistency and signifiers

A pattern is a candidate solution to a recurring problem. Choose it by task, context and observed behavior. [X05, pp. 13–21, 45–48](../books/X05.md#patterns-are-hypotheses-about-familiar-problems)

## DO

- State the problem before browsing examples, then compare candidates by trigger, visibility, representation and result. [X05, pp. 45–48](../books/X05.md#compare-the-mechanism-not-merely-the-screenshot)
- Make the perceived action match the capability: a favorite, save or refresh control does what it implies. [X05, pp. 32–33](../books/X05.md#capability-signifier-and-expectation); see also [X07](../books/X07.md#deliberate-rejection-of-deceptive-controls)
- Keep meaning and repeated behavior consistent while allowing documented variants for different contexts. [X05, pp. 38–44](../books/X05.md#choose-at-several-levels); [S02, pp. 27–41](../books/S02.md#practical-guidance)
- When departing from convention, state the intended improvement and test recognition and task completion. [X05, pp. 24–31](../books/X05.md#evaluate-change-rather-than-copy-convention)

## DON'T

- Do not ship a familiar icon without a label or accessible name for this audience.
- Do not copy hover-only or gesture-only access to an essential action.
- Do not force fixed card dimensions or one component variant everywhere for consistency.
- Do not promise that a pattern produces trust, happiness or conversion. [X05, pp. 8, 22–27](../books/X05.md#unsupported-mechanisms-and-dated-resources)

## Guidelines and example

Resolve the structural need and main flow before polishing isolated controls. Use the source's context/strategy/consistency categories as thinking tools, and test the actual representation with the relevant input methods. [X05, pp. 38–48](../books/X05.md)

For a mobile chatbot, use the existing conversation-list pattern where available and keep send/retry behavior coherent. A public game page can use in-page links instead. Both can share tokens while serving different tasks *(synthesis)*.

## External and internal consistency

External consistency draws on conventions the audience already knows; internal consistency keeps the product's own cues, labels and behavior predictable. Inspect both before changing a pattern. Explain any icon or required-field symbol that departs from them. [U03, pp. 12–23](../books/U03.md)

Keep intentional variants for different roles and states: a primary action and a destructive action look different. Make an exception when it improves a task, document the reason and test the affected behavior. Keep the way out of a flow available. [U03, pp. 24–37](../books/U03.md#purposeful-differences-and-historical-cases)

## Minimalism and necessary complexity

Simplify by removing elements that do not help the task, keeping understandable actions, necessary content and recovery. A restrained aesthetic can still use color, imagery or asymmetry. Alignment is not the same as centering. [U13, pp. 6–18, 22–24, 32–33](../books/U13.md)

Set section and item counts by the content, keep important product details visible without hover, and keep secondary body copy readable. Verify loading speed on the delivered implementation. [U13, pp. 19–28](../books/U13.md#discoverability-and-readability-survive-subtraction)

For a chatbot, fewer nested surfaces improve grouping, while retry and conversation navigation stay. For a game page, expressive artwork carries identity while a short readable release block supports the decision *(synthesis)*.
