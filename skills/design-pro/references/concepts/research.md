# Research and evidence

Select a method for the uncertainty, given product stage, context and available resources. [M02, pp. 13–28](../books/M02.md#research-selection)

## DO

[M02, pp. 15–28, 32–35](../books/M02.md)

- Separate context/motivation from task performance, and attitudes from observed behavior.
- Use early concepts to question assumptions; use functional tasks to examine completion and recovery.
- Define success, error and abandonment before collecting metrics.
- State participant and environment limits when interpreting outcomes.
- Record an action, an inferred motive and an evaluative judgment as three separate notes. [X09, pp. 36–40](../books/X09.md#interviewing-and-interpretation)

Pick the method by its output: card sorting for grouping questions, expert review for candidate issues, contextual work for setting and workarounds, task observation for completion and recovery. A persona summarizes research that was done; eye tracking shows gaze. [X09, pp. 43–49](../books/X09.md#select-research-for-its-output)

## DON'T

See the source's [historical and sample limitations](../books/M02.md#exceptions-contradictions-and-historical-limits).

- Do not count liking a mockup as completing a task; observe the task.
- Do not assume remote testing reproduces natural context; record the setting.
- Do not reuse historical vendor speed claims, prices, incentive amounts or sample rules; get current figures.
- Do not present a fictional user or model walkthrough as real-user research; label it.

## Guidelines and example

For a game page, a task asks someone to find release/platform information and explain the main action. For chat, ask them to recover a failed send. Observe path and result before asking for impressions. Without recruited participants these are test scenarios *(synthesis)*.

## Match the method to the claim

| Uncertainty | Useful method | Evidence limit |
| --- | --- | --- |
| Can someone complete/recover a task? | Observed usability task with relevant people | Record assistance and prototype limits; preference alone is insufficient. |
| Where would people expect content? | Card sort for grouping; tree test for findability | A text hierarchy does not validate the visual navigation. |
| Did usability change over versions? | Comparable benchmark tasks/measures | Keep conditions and participants comparable; a before/after change alone is not causal proof. |
| What happens across repeated use? | Longitudinal/diary work | Track missing entries, burden and self-report limits. |
| How does a task span devices? | One journey across touchpoints | Separate this from different groups attempting the same task on each device. |

Quantitative/qualitative and attitude/behavior are separate dimensions; choose on both for the actual question. [X17, pp. 6–18](../books/X17.md)

Multivariate testing varies several elements and their combinations. Name each check for what it was: model walkthrough, prototype preference exercise, local browser check or production experiment. [Source correction and primary definition](../books/X17.md#experiment-terminology-needs-correction)

In a task script, state the goal and leave the route open: "Find a suitable gift", not "Use search to find a gift". State success and any help given. Report as observation → consequence → possible explanation → proposed change. [X15, pp. 90–96](../books/X15.md#reports-should-preserve-observation-consequence-and-uncertainty)

## Walkthrough, observation and measurement

A cognitive walkthrough predicts, for specified users, whether they would want an action's effect, notice its control, understand the mapping and recognize the feedback. Start from a known correct sequence and a detailed design; record each failed assumption and keep going. Report the results as predictions. [U06, PDF pp. 66–74](../books/U06.md#cognitive-walkthrough-a-predicted-first-use-path)

Independent heuristic reviews and task walkthroughs cover different gaps; report several perspectives run by one model as one evaluator. Use an informal action sequence to expose prerequisites, memory/transcription effort and recovery before investing in timing models. [U06, PDF pp. 74–95](../books/U06.md#action-analysis-and-heuristics-answer-different-questions)

In observed testing, use neutral prompts, record assistance, and keep unexpected choices and prototype limits in the record. Stop respectfully and honestly when needed. For an incomplete task, record the actual stopping condition and elapsed time. [U06, PDF pp. 97–116](../books/U06.md#usability-testing-assistance-and-participant-protection)

For quantitative claims, define the measure, sample, treatment of failures/missing data and uncertainty before interpreting differences. Use a current statistical reference; U06's recipes contain errors, noted in the [source correction](../books/U06.md#statistical-recipes-require-correction).
