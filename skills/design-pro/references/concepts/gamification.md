# Gamification, motivation and progress

Use game-related mechanisms only when they support an outcome the person already values. A reward system is not a substitute for a useful task. [X16, pp. 6–17](../books/X16.md#conditions-tradeoffs-and-exceptions)

## DO

- Define the desired user benefit and what real progress means.
- Show completed and ongoing work accurately; allow meaningful self-set goals where appropriate.
- Let people decline competition/rewards and stop without losing unrelated capabilities.
- Evaluate task quality and unwanted pressure alongside repeated use. These last safeguards are design-pro qualifications of the source's addiction rhetoric. [X16, pp. 15–28](../books/X16.md)

## DON'T

- Do not add points, badges, streaks or artificial scarcity automatically.
- Do not equate time spent, popularity or activity counts with learning, expertise, health or task completion.
- Do not hide essential controls to create a discovery reward, or interrupt every action with celebration.
- Do not assume all external rewards help or all external rewards harm; the source itself presents conflicting positions. [X16, pp. 14–27](../books/X16.md)

## Guidelines and example

The trigger/action/reward/investment model can describe a proposed loop; it does not guarantee behavior. Ask what each repetition produces, whether the measure can be gamed, and whether the person can leave. A visible “done” area can be enough for task tracking without a currency. [X16, pp. 9–10, 22–24](../books/X16.md)

A game-release page need not turn browsing into a game. A chatbot can preserve useful work without rewarding unnecessary messages. Compare actual task success and reported pressure if studying an incentive change; local browser checks only verify the implemented behavior. These are design-pro examples for both modes, not effectiveness findings.
