# Information architecture and task flows

Organize content so people can predict where to find what supports their task. Distinguish content relationships, interface navigation and the sequence of actions; a menu screenshot alone does not define all three. [X10, pp. 60–71](../books/X10.md#information-architecture-and-findability); [X06, pp. 13–19](../books/X06.md)

## DO

- Start with the goal and actual content, then choose useful categories/metadata using evidence about the audience. [X10, pp. 61–64](../books/X10.md)
- Use recognizable, honest labels and show representative deeper content when it helps set expectations. [X10, pp. 62–64](../books/X10.md)
- Map a task's choices, transitions, result and recovery before polishing isolated screens. The written auto-deposit flow shows one way to explore this. [X10, pp. 29–31](../books/X10.md#usability-task-structure-and-recovery)
- Use a story for action/outcome, a scenario for circumstances, and a flow for paths. Keep research evidence separate from fictional examples. [X06, pp. 13–15](../books/X06.md#link-people-situations-and-paths)
- Plan who maintains necessary content and terms. A sitemap, taxonomy and content repository solve different needs. [X06, pp. 16–19](../books/X06.md#plan-for-content-maintenance-early)

## DON'T

- Do not organize every product by the company's departments or by a fashionable template.
- Do not impose a three-click limit when a longer set of understandable steps better supports the task. [X10, p. 24](../books/X10.md)
- Do not force a sitemap, persona or separate screen for each decision in a narrow component request. Choose the useful artifact. [X06, pp. 18–23](../books/X06.md)
- Do not hide necessary mobile capability in a desktop-only future step or use broad categories unsupported by the actual content. [X09, pp. 60–62](../books/X09.md#mobile-web-qualifications)

The first caution is design-pro synthesis; the historical source's format-based navigation prohibition is also qualified: a visitor explicitly seeking a gameplay video may benefit from that format label. [X10, pp. 63–64](../books/X10.md)

## Guidelines and example

Use open card sorting to explore groupings, closed sorting to examine given categories, tree testing to investigate label paths, and click testing to examine a visible starting choice. Follow with actual task flow where needed; none alone verifies the entire application. [X10, pp. 70–71](../books/X10.md)

A game-release page may need one page with meaningful sections for identity, gameplay, release/platform details and the main action. Chat may need a conversation list, active transcript and composition/recovery states, with responsive presentation sharing the same underlying task. These are design-pro demo assumptions to test, not universal architecture prescriptions.
