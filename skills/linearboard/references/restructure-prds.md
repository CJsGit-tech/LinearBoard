# Restructure existing PRDs

Read this reference only when the user authorizes reorganizing existing PRD records. A read-only length/style review does not authorize this mutation.

1. Read the current PRDs, every source US, native relations/labels/milestones/states, milestone summary and QA record. Inventory current requirements and acceptance behavior; distinguish duplicates, superseded content, conditional future work and design/engineering follow-up.
2. Use approved task boundaries. Reuse the issue that best matches each retained task and create only genuinely missing PRDs. Do not impose a product-specific count, repurpose historical IDs or change lifecycle merely to tidy the structure.
3. Before replacing bodies, preserve useful decision history in native PRD revisions/comments or an existing explicitly authorized QA document and read it back. Deduplicate identical entries without losing different answers, provenance or corrections. Do not create a second QA document for reorganization.
4. Record old requirement IDs to new owners/canonical rules. Preserve stable IDs and aliases/lineage where practical. Account for shared, future and not-applicable rules; never discard them silently or reactivate historical alternatives.
5. Rewrite each PRD with current behavior only using the five-section template. Keep milestone-wide constraints in the existing milestone document and task-specific rules locally understandable. Preserve source-story links and useful unrelated relations/labels.
6. New PRDs inherit the actual source milestone and document/story provenance; native source relations apply only to actual legacy issue sources, while M/US labels are optional. Cite explicit user decisions for approved capability beyond story wording; do not invent or rewrite source stories.
7. Update cross-links and the milestone PRD index after real issue IDs exist. Keep each rule in one primary owner; related PRDs retain only the local precondition and link needed for comprehension.
8. Retrieve every affected PRD, source story, any existing QA and milestone document. Verify each old requirement's disposition, acceptance coverage, reciprocal relations, labels, milestone, readable links, retained states and unchanged source-story content.

Shorter prose alone is not success. Preserve all confirmed requirements and exceptions while removing duplication. Keep excluded historical issues intact unless a separate lifecycle change was explicitly authorized.
