# Debug a reported problem

Use `debug [Project] [Milestone] [report or issue IDs]`. The BUG ticket owns the report, investigation, evidence and result. A report may come from chat, a screenshot, a document or an existing issue. Resolve the destination and selected reports before writing.

1. **Record the report before investigating.** The coding agent searches for a matching active ticket, then directly creates or reuses one ticket per independently verifiable defect. Use `BUG {feature} — {observed problem}` for new tickets. Preserve the user’s observation, expected behavior, evidence and reproduction context. If the expectation is unclear, record the open question and resolve it before changing behavior. Keep repeated reports on the same active ticket. A recurrence after review or completion gets a linked follow-up. Preserve historical records.
2. **Connect the issue.** Apply the native project and milestone, applicable M/US labels, Coder and exactly one FrontEnd or BackEnd Category. Start new tickets in Backlog. Link the relevant story, PRD, design and delivery records. Use native Related for issue sources, direct links for document sections and Blocks only for actual prerequisites. Verify the issue and its project/category View. Triage-only ends here.
3. **Investigate and fix.** Reproduce the reported path, test likely causes, and make the bounded change supported by the evidence. Check the original failure and relevant regressions. For UI work operate the actual target application. Use the applicable plan, independent review and evidence rules in [coding dispatch](coding-dispatch.md); the coding agent owns its BUG ticket and comment directly.
4. **Comment on that ticket.** The coding agent posts a concise native issue comment: **Status** (fixed, partial or blocked), **Why** (verified cause or still unknown), **Action** (what changed or was attempted), and **Check** (observed result and remaining limits). Read back the comment. On retry, reuse the existing matching result instead of duplicating it. The assigned delivery reviewer independently verifies the result, records evidence and applies the [shared status policy](../SKILL.md#review-handoff-and-final-acceptance). If the agent cannot write its own ticket or comment, report the access gap.

A new product request or a disputed requirement goes through the [sync review](sync.md) for proposed record changes.
