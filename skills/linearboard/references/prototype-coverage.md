# React Native prototype checklist

Use this checklist to map what the user can do, what the interface shows, and how the user continues when something changes. Start from the scoped stories, PRDs, acceptance criteria and platform. Add only applicable cases. Resolve missing product rules with the owner before designing the dependent behavior.

## Components, states and interactions

- [ ] **Navigation and transitions.** Check entry, forward and Back paths, tabs or steps, and whether the selected item, filters, scroll position or unsaved changes should survive. For motion, name its purpose and check interruption and reduced motion where applicable. Use the [interaction handoff](interaction-loading-motion.md) for timing and input rules.
- [ ] **Controls and forms.** Check buttons, fields, toggles, checkboxes, dropdowns and pickers that appear in the flow. Cover resting, focused, pressed, selected, disabled and invalid states as applicable. For a dropdown, operate it open, choose an option, dismiss without changes, and check focus return. On failed submission, check what input stays and how to retry.
- [ ] **Overlays and confirmations.** Check the relevant dialogs, sheets, popovers or tooltips. Specify what opens them, what can dismiss them, what confirm and cancel do, and where focus goes after closing. Check any confirmation or undo behavior agreed for risky actions.
- [ ] **Loading and recovery.** Check initial load, refresh or submission while pending, and the outcomes the flow can reach. Show what remains usable and whether the user can cancel or retry. Distinguish an empty list, no search matches, offline or failed loading when each needs a different next action.
- [ ] **Messages and status.** Check inline validation, temporary confirmations, persistent warnings and status badges where applicable. Specify copy, trigger, location, dismissal or persistence, and the next action. A badge needs a clear meaning in text. If it opens a menu or filters results, exercise that interaction too.
- [ ] **Layout and access.** Try realistic content, long labels and scoped sizes. Check wrapping, clipping, scrolling, touch targets, accessible names, focus order and contrast. Check that important messages and state changes can be understood without color or motion alone. Mark any assistive technology checks that were unavailable.

## Product account permissions

- [ ] **Map role, resource and action.** For each restricted action, derive who can see or do it and on which records from confirmed sources. Include own versus another person's record or workspace membership only where that distinction applies. Decide whether to hide or disable the entry point, what a direct attempt shows, and where the user can go next. Ask about missing rules and avoid inventing roles or grants.
- [ ] **Build a test account switcher.** For flows with account permissions, put **Switch test account** in the prototype's review menu. Use fictional accounts backed by local data. Give each account a name, its role or access level, and its permissions for the scoped app and workspace or records where applicable. Show the active account and access level. Changing accounts must update the permissions used by navigation, screen data and actions, so reviewers can run the same flow as different accounts without restarting or signing in to a real service.
- [ ] **Operate the same flow before and after switching.** For example, if the PRD lets a Member edit a task and a Viewer only read it, complete the edit as Member. Switch to Viewer, check the visible controls, then try the same edit route directly and check the denial and return path. If the current screen becomes restricted after a switch, show the approved denial or return to an allowed screen. Check that the previous account's restricted data cannot reappear via Back or a late response, and that switching back restores the correct access. Review menu shortcuts must run the same simulated checks as ordinary navigation.
- [ ] **Cover changes in access when relevant.** Check signed-out, expired session, pending invitation or revoked access only when the scoped flow can reach them. Define where the user lands, what data stays safe to retain, and whether they can sign in, return, or request access. For device permissions such as camera or location, show when the system prompt appears, why access is needed and what grant or denial leads to. Use the platform's expected prompt and a useful fallback. [Apple privacy guidance](https://developer.apple.com/design/human-interface-guidelines/privacy/)

The switcher belongs in the prototype's review tools. Simulate sign-in and access using local data. Verifying that the real app enforces access on every request belongs to delivery review.

## Use the checklist in each command

- **`create-designs`** · Pick the scoped journey and the states that affect a fair comparison. Give A, B and C the same test accounts, permissions, sample data, starting state and behavior. Operate the relevant cases in each proposal. Once the user selects a direction, record applicable state and permission rules in the owning screen specification and link the requirements. Carry remaining coverage into `create-visuals`.
- **`create-visuals`** · Extend the selected proposal's test accounts and permissions across the full scoped set. Make each case reachable through the actual flow or a named fixture in the review menu. On the requested runtime, exercise the trigger, outcome and return or recovery path. Report observed results, applicable checks still blocked, and the exact visual version by screen ID. Complete the required checks before requesting approval for that set.

Keep proposal notes in chat until the style is selected. Record confirmed decisions and later review coverage in the existing LinearBoard specification or comment. Use a compact entry such as `SCREEN-03 / Viewer / Edit → access denied → Back / verified on iOS simulator`. Skip unrelated cases and call out meaningful exclusions or blockers.

## If a designer works alongside the prototype in Figma

1. Name frames and flow starting points using the same screen IDs and scenarios as the React Native review menu. Use [Auto Layout](https://help.figma.com/hc/en-us/articles/360040451373-Guide-to-auto-layout-in-Figma) for changing content and [component variants](https://help.figma.com/hc/en-us/articles/360056440594-Create-and-use-variants) for reusable states.
2. Connect the main path and representative alternate paths. Use [overlays](https://help.figma.com/hc/en-us/articles/360039818254-Create-overlays-in-your-prototypes) for menus and dialogs. If useful, use [variables and conditions](https://help.figma.com/hc/en-us/articles/17146044893591-Advanced-prototyping-examples) to simulate a role or an outcome such as failed save. Figma interactions model the flow. Operate the React Native counterpart to verify it on the scoped platform.
3. Keep Figma file access separate from the roles modeled inside the app. Give co-designers edit access and reviewers view access for comments, subject to the workspace's sharing settings. Use supplied links within their existing access. Changing sharing or editing the Figma file requires its own authorization. [Figma sharing and permissions](https://help.figma.com/hc/en-us/articles/360040531773-Share-files-and-prototypes)
4. Reconcile differences by screen ID, scenario and version. Share the Figma review link in chat when available. Keep confirmed behavior and approvals in LinearBoard and the runnable review in React Native. [Figma Dev Mode](https://help.figma.com/hc/en-us/articles/15023124644247-Guide-to-Dev-Mode-in-Figma) can help inspect layout and annotations when available.
