# Create a vision document

Create or revise a native LinearBoard Project Document from the Planning discussion. Use What, Why, Who, Where and How to guide drafting.

## Inputs and destination

Use the supplied context and the current chat as inputs, including decisions made outside a formal planning exchange. Identify the key choices the user made or accepted that shape the vision. Apply later corrections to earlier ideas, and leave unchosen suggestions out. Weave the effect of those decisions into the narrative. Do not restart a requirements interview or force one product type into the other's framing. Ask only when a missing answer materially changes the vision; leave undecided details out of the narrative.

Resolve the team/project and search native Project Documents by purpose and title. Reuse the canonical vision and preserve its established title. A link or attachment is not a native Project Document. Do not create an additional planning document for the same vision.

## 4W1H content

Follow the five questions in [the vision template](../assets/templates/vision-template.md). Preserve the terms used during planning and write in the user's preferred response language.

For new and revised visions, use the five visible second-level headings from the template by default. Write concise prose under each heading. Weave in a constraint only when it helps the reader picture the idea. Keep research notes, sources and unresolved questions in the discussion.

## Make key phrases stand out

When creating or revising a vision, choose the shortest phrases that carry the product’s main benefit, distinguish a role, or express a decision that changes what happens. Use native Markdown to bold those phrases and keep the surrounding explanation in regular text. For example, write “If two customers try for the last place, **only one booking is confirmed**.” Use italics for named screens or actions such as *My Schedule*, and bullets when readers need to compare roles or follow distinct steps. Use the editor’s theme for fonts and colors.

## Save and verify

Save under the resolved native project parent and read back full content, title, project placement and links. Scan the headings and emphasized phrases together to verify that they convey the agreed priorities. Check the saved paragraphs against the chat’s key vision decisions, including corrections, and verify that the saved vision contains each template heading once, in order, with content beneath it, unless the user explicitly requested a different format. Preserve useful history and unrelated content. For a substantive direction change, identify affected existing milestones/PRDs/design records and state which remain unsynchronized; this command does not authorize rewriting them.

Return the canonical document URL and material unknowns. Do not create milestones, stories, issues or implementation work. Determine a next recommendation from current records rather than assuming a later stage is missing.
