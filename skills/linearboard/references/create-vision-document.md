# Create a vision document

Create or revise a native LinearBoard Project Document from the Planning discussion. Its purpose is to express the product vision in **4W1H: What, Why, Who, Where and How**.

## Inputs and destination

Reuse the planning discussion, supplied sources and current project context. For a business product, retain the pain and intended solution. For a game, retain the intended play and player experience. Do not restart a requirements interview or force one product type into the other's framing. Ask only when a missing answer materially changes the vision; mark nonblocking unknowns as undecided.

Resolve the team/project and search native Project Documents by purpose and title. Reuse the canonical vision and preserve its established title. A link or attachment is not a native Project Document. Do not create an additional planning document for the same vision.

## 4W1H content

Use [the vision template](../assets/templates/vision-template.md) in the user's language:

- **What:** the product being envisioned and the central value or intended play experience.
- **Why:** the pain/unmet need and desired improvement for a business product; the experience, feeling or appeal the game should offer for a game.
- **Who:** intended users or players and relevant broad roles.
- **Where:** intended usage/play situation and platform when known. Leave unknown platform or context open rather than choosing it silently.
- **How:** the high-level solution approach or core play/experience loop. Keep implementation architecture and detailed product rules for later stages.

`When` is not a required sixth section; include timing only when the user actually supplies a relevant constraint. Preserve confirmed boundaries, sources and material open questions concisely. Do not invent commercial validation, platform capabilities, market evidence, dates, owners, metrics or approvals. Distinguish confirmed direction, proposals and unknowns.

## Save and verify

Save under the resolved native project parent and read back full content, title, project placement and links. Preserve useful history and unrelated content. For a substantive direction change, identify affected existing milestones/PRDs/design records and state which remain unsynchronized; this command does not authorize rewriting them.

Return the canonical document URL and material unknowns. Do not create milestones, stories, issues or implementation work. Determine a next recommendation from current records rather than assuming a later stage is missing.
