The playbook

01 / Setup

這些是 Codex 指令，不是 Terminal 指令。

在 Codex 對話中選取 linearboard skill，或直接貼上以下文字：

CODEX PROMPT
$linearboard help
  1. 確認本機 LinearBoard 預設服務是 http://127.0.0.1:8765，或明確提供另一個 loopback URL。
  2. 指定真正存在的 team、project 與 milestone；不要用目前瀏覽器頁面或資料夾名稱猜目的地。
  3. 檢查回傳的 LinearBoard document、issue 與 View 連結，以及讀回後的欄位與關聯。
  4. 把「討論」、「建立紀錄」、「派工實作」、「In Review」與最終使用者接受分開。
若 connected linearboard_* tools 不可用，skill 會改用 scripts/operate.py 進行服務 preflight 與操作。這不是改用 Linear SaaS。
02 / Choose a path

不用每次從第一步重跑。

從第一個尚未完成的產出接續。已確認的回答、既有 issues、核准視覺與目前程式狀態應被重用。

願景／Milestones→ Stories／PRDs→ Design documents→ 三版面／全套視覺／核准→ Design／FE／BE issues→ Checkpoints→ Dispatch／Review
從零開始

只有產品構想

planning → create-vision-document → create-milestones → create-userstories → create-PRDs

先建立可追溯需求，再進入設計。產品決策仍未確定時，用 prd-demystify 一次處理一題。

延續現有專案

需求、設計或開發票已存在

sync（有差異才用） → 下一個缺少的產出 → organize-task-batch → dispatch

不要為了遵守指令順序而重做已完成文件，也不要把 read-only 規劃誤當成實作授權。

先建票，後派工。 create-issues-FE／create-issues-BE 只建立 Backlog issues 與 saved Views；dispatch 才讓 agents 實作。
03 / Local system of record

LinearBoard App 是唯一產品工作紀錄。

放在 LinearBoard

產品與交付紀錄

PRDs、Stories、acceptance criteria、決策、研究摘要、issue 狀態、dispatch records、agent reports、驗證證據與 approvals。

放在 repository

工程產物

Source code、tests、config、migrations、runtime assets、可重現產物與 AGENTS.md。不要在 repo 建第二份 backlog 或 agent report archive。

Database

PostgreSQL-backed

應透過 App／tools 操作；不可直接改 database 或 legacy SQLite backup。

Deletion

Recoverable trash

先做 impact preview；record deletion 進入可復原垃圾桶，永久刪除留給使用者 UI。

Visual exception

Read-only gallery

create-visuals 的 HTML gallery 可留在本機供審閱，但不能成為 approval 或 PM mirror。

如果 LinearBoard、workspace、team、project 或必要權限不可用，停止受影響操作並回報 blocker；不要改存本機文件或切換到 Linear SaaS。
04 / Intent → Stories

願景、里程碑與 User Stories

願景說明為誰解決什麼問題；Milestone 定義一階段的可觀察成果；User Story 保持在使用者結果與 acceptance criteria。

05 / Product rules

PRDs 與逐題釐清

PRD 可以涵蓋多個 User Stories，但每條規則要有唯一主要負責位置。未回答的選項是 unresolved，不是默認同意。

06 / Design → Approval

設計文件、三版面與完整視覺審閱

create-designs 與 create-visuals 是兩個不同階段。前者只建立設計文件；後者先選本次 layout，再完成全套 screens／components 與 key states。

核准順序：三個代表性 layout → 使用者選擇本次 layout → 產生完整範圍與關鍵狀態 → 選定 final images 並授權 upload → 使用者核准完整設計範圍 → 建立或重用 Design tickets 與 Design View。
07 / Delivery planning

FE／BE issues 與 checkpoints

Issue creation 會建立或重用 saved category View，但不會 dispatch。技術查核與選型在 FE／BE 建票內部進行，不是另一個使用者指令。

Ownership

一票一個可審閱責任

共用 data model、stable identity、file format 或 service interface 只指定一個 owner。

Relations

Native dependency

真實 prerequisite 使用 Blocks／Blocked by；來源 Stories／PRDs 保留 Related 與 body links。

Views

Saved, not filtered

Label 或暫時篩選不是 View。建票完成要驗證 View 條件、位置與完整 membership。

08 / Dispatch → Review

派工、獨立驗證與 final acceptance

In Progress

仍需實作或修復

產品缺陷、核心流程未驗證或 attribution 不明時，不能交審。

In Review

可供使用者審閱

Implementation complete，TPM 已做獨立檢查並記錄證據；不等於 production ready。

Done

只由 final user 決定

TPM 與 coding agents 都不能代替使用者接受交付。

Agent lifecycle：worker 先讀來源並回報 acknowledged／blocked；TPM 驗證 plan 後才放行 implementation。Worker report 是 claim，TPM 仍需檢查 source／deployment、執行適當 checks，且只有 TPM 能寫 LinearBoard。
09 / Maintenance

Debug 與授權範圍內的同步

Debug 要保留原始使用者回報、修復票與獨立驗證；sync 只修正有確認證據的差異，不會啟動實作。

10 / Practice

常見問題

本機服務沒啟動，可以直接改資料庫嗎？

不可以。使用 connected tools 或 scripts/operate.py 的 preflight；不可直接修改 PostgreSQL、legacy SQLite 或另建 PM database。

create-designs 為什麼沒有 Design issues？

目前規則是 document-only：只建立 design overview 與 screen／interaction specification。Design tickets 要等 create-visuals 的完整設計範圍明確核准後才建立。

已經選過 theme，為什麼還要三個 layouts？

Theme 決定 colors、typography 與 component language；不等於這次 surface 的 layout。每個新 layout scope 仍要先產生 exactly three representative layouts。

View 看不到正確 issues，應該改 issue 狀態嗎？

先修 View filters 與 membership。Saved View 應依 project 與精確 Category 組合；不要為了配合錯誤 View 改 issue 狀態或 labels。

Worker 說 completed，可以直接移到 Done 嗎？

不行。TPM 必須獨立驗證後才能交到 In Review；Done 永遠由 final user 決定。

測試環境限制是否一定卡在 In Progress？

只有狹窄、已明確 attribution 的 environment-only limitation，可以在主要 target 與流程已檢查、其他證據支持 review readiness 時保留於 In Review；該檢查必須標示 Not tested 或 Environment-blocked，不能寫 Pass。

最後檢查

從現況接續，讓每一步都有來源、授權與證據。

選正確指令；確認目的地；讀回 canonical records；準備好才派工；驗證後交給使用者接受。
