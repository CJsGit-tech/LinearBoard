01 / Workflow

Continue from the first missing step

This is a reference path, not a command to execute all stages. Request each writing or execution step separately. Reuse valid existing outputs.

Idea→Vision→Milestones + grouped stories→PRDs→Design specifications→Complete-set visual approval→FE / BE issues→Dispatch→Review and acceptance

Starting with an idea

Discuss it with planning. Once confirmed, save the vision, then derive stories and group them into milestones. Do not jump straight to dispatch.

Requirements or implementation already exist

Read current records and find the first missing deliverable. Use prd-demystify for consequential open PRD decisions. Use organize-task-batch when multiple ready issues need checkpoint ordering.

Skip design stages only for confirmed BE-only or non-visual scope supported by canonical requirements.
02 / Setup

Replace the placeholders first

Paste these skill prompts into Codex, not Terminal. This guide generates text only. It never calls the app API, dispatches workers, or edits project records.

<Team> / <Project> / <Milestone>
<Issue IDs> · <Repo path> · <App URL or run target>
  • <Project> names the LinearBoard project. <Repo path> identifies the source-code directory.
  • Use the actual milestone name or a uniquely resolvable ID for <Milestone>. Do not assume the first milestone is M1.
  • Use actual issue identifiers from the app for <Issue IDs>. Replace every remaining placeholder before submitting.

Startup and storage

The default app address is http://127.0.0.1:8765. The operate.py client runs preflight automatically. It reuses a healthy service; if stopped, it checks the existing Docker Compose deployment, secret, and PostgreSQL volume before starting it. Codex runs the same preflight before connected MCP tools.

If deployment files, volume, image, or permissions are unavailable, affected operations stop and report the blocker. Preflight does not create a replacement database, migrate data, or switch to legacy SQLite.

Product-work records

Vision, stories, PRDs, decisions, design specifications, issues, dispatch records, and verification belong in LinearBoard’s PostgreSQL-backed app. Do not maintain PM copies in the repository.

Engineering and visual artifacts

Code, tests, and configuration stay in the repository. The read-only create-visuals gallery and imagegen originals may remain locally for visual review. Approval and status remain canonical app records.

04 / Planning

create-milestones

Group stories into milestones

Writes milestones and a document
Prepare
The vision, confirmed scope, and existing milestones or stories.
Expect
Native milestones and one milestone-overview document containing grouped stories with stable US IDs, anchors, and a structural index.
Check
Check native records under Milestones. In the overview document, each story has core acceptance and belongs to one native milestone. The index matches the readable sections.
$linearboard create-milestones <Project>
Derive stories from the existing vision and group them by observable outcomes. Reuse existing milestone and story IDs. Do not invent dates.

Creates no UserStory issues or UserStories View. Preserves existing legacy story issues.

05 / Requirements

create-PRDs

Create traceable product requirements

Writes PRD issues and a View
Prepare
The story document for <Milestone>, stable US IDs, and confirmed rules.
Expect
ProductRequirement issues, source document/story links, native milestone associations, and a <Project>-PRDs saved View.
Check
Open each PRD. Check source story sections, the native milestone, actual document and story IDs in the source index, and expected View membership.
$linearboard create-PRDs <Project> <Milestone>
Create or reuse PRDs from the milestone’s grouped stories. Keep unresolved questions explicit. Create or reuse the PRDs View and verify its members.

New issues start in Backlog. M/US labels are optional aids; preserve existing labels. Do not invent issue relations for document sections.

06 / Requirements

prd-demystify

Clarify decisions in the owning PRDs

Updates existing PRDs
Prepare
Existing PRDs, source stories, and unresolved product scope or boundary decisions.
Expect
Confirmed answers applied directly to the owning PRDs, with native comments when needed to preserve history.
Check
After each consequential answer, reopen the PRD and check that its behavior and acceptance reflect the decision. Unanswered questions remain open.
$linearboard prd-demystify <Project> <Milestone>
Read existing answers first. Ask only unresolved questions that affect product scope or acceptance, one at a time. Apply confirmed answers directly to the owning PRDs.

Creates no separate QA document, does not rewrite historical QA documents, and does not change issue status.

07 / Design

create-designs

Save the design direction and interaction specification

Writes two documents
Prepare
Source stories, PRDs, confirmed decisions, and available references.
Expect
Two Project Documents: a design overview and a screen/interaction specification, with a product-specific direction and concrete recommendation.
Check
Check that the documents link to each other, screens/flows trace to requirements, and entry points, actions, and applicable loading/empty/error states are specified.
$linearboard create-designs <Project> <Milestone>
References: <Design references>
Constraints and preferences: <Design constraints>
Inspect the references, recommend a direction, and save the design overview and screen/interaction specification.

Documents only. Generates no images and creates no Design issues or View.

08 / Design

create-visuals

Review layouts and the complete visual set

Generates images; uploads and creates tickets when authorized
Prepare
Existing design specifications, the requested screens/components/states, and any approved direction.
Expect
imagegen studies and a read-only gallery; after complete-set design approval, Design tickets and a <Project>-Designs View.
Check
Confirm coverage and generation batches first. Inspect every image and the gallery. After layout selection, complete the requested detail scope. Read back attachments, Design tickets, and the View after approval.
$linearboard create-visuals <Project> <Milestone>
Requested scope: <Screens, components and key states>
State coverage and generation batches first. Use a scope-sized comparison for a new composition; directly edit the selected layout for bounded changes. Preserve imagegen originals.
Follow-up prompt examples
After selecting a layout, reply: “Choose <Layout> and continue the originally requested complete screen/state coverage.” For upload, specify: “Upload <Exact versions> to the owning specification document.” After reviewing the full set, specify: “Approve the complete design scope <Exact screen/version inventory>; create or reuse Design tickets and the View.” The native attachment approved field remains a user action in the app. Codex must not set it on your behalf.

For new compositions, normally compare two or three representative layouts. Edit a selected layout directly for bounded fixes. Layout selection, upload, complete-set design approval, and native attachment approval are separate gates.

11 / Delivery

organize-task-batch

Propose reviewable delivery checkpoints

Read-only
Prepare
Existing FE/BE issues, source records, and dependencies; optionally <Issue IDs>.
Expect
An ordered proposal in chat: Batch Name, FE Issues, BE Issues, grouping rationale, and Expected Checkpoint Outcomes.
Check
Every selected issue appears once or has an exclusion reason. Each checkpoint has observable outcomes and clear prerequisites.
$linearboard organize-task-batch <Project> <Milestone> <Issue IDs>
Propose reviewable checkpoints based on existing dependencies. Include exclusions and blockers. Proposal only: do not save records or dispatch.
Follow-up prompt examples
To save a confirmed proposal in the app’s Delivery page, explicitly request: “Save the confirmed <Batch proposal> as delivery batches for <Project>, retaining the exact issue IDs. Do not dispatch.”

Does not save batches, edit issues, or implement. Batch size is not the three-worker concurrency limit.

12 / Delivery

dispatch

Implement the authorized delivery scope

Dispatches, implements, and independently verifies
Prepare
Exact issue IDs or an existing, resolvable Batch; required sources, designs, repository, and an accessible execution target.
Expect
Dispatch records, validated worker plans, implementation reports, independent TPM evidence, and an In Review handoff for reviewable work.
Check
Verify the main flow through the actual app’s normal entry point. Report results, environment limits, and remaining checks; read back issues and dispatch records.
$linearboard dispatch <Project> <Milestone> <Issue IDs>
Repository: <Repo path>
Actual verification target: <App URL or run target>
Dispatch only the specified IDs after checking sources, dependencies, approved designs, and target access. Verify the work and hand it off for review. Do not set Done.
Follow-up prompt examples
For a saved batch, replace the first line with: $linearboard dispatch <Project> <Milestone> Batch <Batch number> The batch must already exist and resolve to exact IDs. A read-only proposal from the previous step is not a saved batch.

Run readiness preflight first. Stop at missing required gates. At most three concurrent workers; workers never write to LinearBoard. The user decides Done.

14 / Maintenance

sync

Reconcile confirmed records and UI evidence

Updates bounded scope
Prepare
<Scope>, confirmed sources, affected issues/specifications, and the current UI.
Expect
A difference report and verified updates. For UI changes, refreshed actual UI screenshots, attachments, and the owning specification index.
Check
Report Updated / Already aligned / Conflict / Unverified separately. Classify screenshots as Missing / Stale / Consistent / Unverified. Read back content, relationships, and rendered images.
$linearboard sync <Project> <Milestone> <Scope>
Reconcile only confirmed records within this scope. For changed UI, inspect missing/stale screenshot coverage, capture the actual interface, and verify uploaded evidence. Preserve history. Do not implement.

Does not implement, replace actual screenshots with imagegen, automatically change status/approval, or overwrite solely because a timestamp is newer. Image cleanup needs separate authorization.

06 / Review

Distinguish saving, approval, and acceptance

What you seeWhat it meansWhat remains
A document or PRD was savedThe record exists. Scope decisions may remain open.Read back content, sources, and native relationships. Resolve gaps that affect later work.
A layout was selectedThe composition direction is chosen.Complete the originally requested screens, components, and key states.
The complete design set was approvedThe user approved an exact screen/version inventory.Verify Design tickets, the Designs View, and accessible exact references. Report the native attachment field separately.
In ReviewImplementation is complete and independently checked by the TPM, ready for user review.The user tests and decides whether to accept. Environment limitations and untested checks remain explicit.
DoneThe final user accepted the delivery.The user makes the decision and changes the state in the app. Codex does not decide on their behalf.

Check saved Views

PRDs, Designs, FE, and BE are persisted category Views. By default they appear as project tabs and span all project milestones and statuses. Use shared placement or narrower filters only when requested. Reuse existing custom Views and verify actual membership; an unsaved filter is not a saved View.

Find the records in the app

  • Documents: vision, grouped milestone/story overview, design overview and screen/interaction specification, and the Bugs report log.
  • Milestones: native milestone records. Story grouping remains in the overview document.
  • Issues and category Views: PRDs, Design tickets, FE/BE delivery issues, and FIX issues.
  • Delivery beneath the selected project in the sidebar: saved batches and dispatch records. A read-only batch proposal does not appear automatically.
A worker report, passing tests, or a successful upload response alone does not prove the full flow. Independently inspect the actual app, source records, relationships, and applicable evidence.
07 / Troubleshooting

Common questions

Cannot find the project, team, or milestone?

Provide a uniquely identifying name or link. Codex follows all list pages and checks the destination before creating anything. Similar names are not grounds for a duplicate. A new product gets only the minimal project container needed for explicitly authorized outputs when destination and scope are clear.

Will repeating a command create duplicates?

The workflow should inspect current state and reuse matching documents, issues, and Views. The API does not deduplicate titles automatically. After partial success, retry only the missing work rather than replaying every creation.

What if an update has a version conflict?

Read the latest version and reconcile differences. Do not force an overwrite. Preserve history, relationships, and out-of-scope content.

Is a missing UserStories View a skipped step?

No new story issues or View are produced by the merged create-milestones workflow. Stories live in the grouped document. Existing UserStory issues and Views remain available as historical sources.

How do deletion and restore work?

Explicitly identify the records to remove. Preview the impact before moving them to recoverable trash. There is no archive concept. Restore required teams/projects/parents first. Permanent deletion requires the user’s manual confirmation in the app. This guide executes no deletion.

Why did a dispatch record not start a worker?

The app stores records and exposes the API. Codex orchestrates the command; imagegen creates visuals; coding agents implement changes. Creating a dispatch row alone does not start a worker. Missing execution tools must be reported as a blocker.

What if the test or execution environment is unavailable?

Report the exact environment, affected criterion, and verified scope. Keep unavailable checks Not tested or Environment-blocked. Unverified core flows and product defects block review readiness. Only a narrowly evidenced environment limitation may accompany an otherwise reviewable handoff under the skill’s rules.
