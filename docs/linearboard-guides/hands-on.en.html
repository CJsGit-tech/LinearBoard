01 / Workflow

Continue from the first missing step

This is a reference path, not a command to execute all stages. Request each writing or execution step separately. Reuse valid existing outputs.

Idea→Vision→Technical baseline (if needed)→Milestones + grouped stories→PRDs + decisions→Three proposals + style choice→Full visual approval + Design tickets→FE / BE issues→Batch labels (if needed)→Dispatch→Review and acceptance

Starting with an idea

Discuss the idea in planning. Save the vision, then record any shared technical constraints before grouping milestone stories.

Continuing existing work

Reuse verified outputs. Skip design for confirmed backend-only or non-visual work. If you explicitly choose approved static visuals, skip the prototype stages when accessible JPGs and recorded approval cover the exact scope and version. Dispatch only when the exact delivery selection passes readiness.

The final Recommended next step block names the reply needed to continue, or recommends a command and explains why. When both are useful, it shows a focused option and a wider set of ready scopes for that command. You choose what to run. See a worked example.
02 / Setup

Replace the placeholders first

Paste these skill prompts into Codex, not Terminal. This guide generates text only. It never calls the app API, dispatches workers, or edits project records.

<Team> / <Project> / <Milestone>
<Issue IDs> · <Repo path> · <App URL or run target>
  • <Project> names the LinearBoard project. <Repo path> identifies the source-code directory.
  • Use the actual milestone name or a uniquely resolvable ID for <Milestone>. Do not assume the first milestone is M1.
  • Use actual issue identifiers from the app for <Issue IDs>. Replace every remaining placeholder before submitting.

Startup and storage

The default app address is http://127.0.0.1:8765. The operate.py client runs preflight automatically. It reuses a healthy service; if stopped, it checks the existing Docker Compose deployment, secret, and PostgreSQL volume before starting it. Codex runs the same preflight before connected MCP tools.

If deployment files, volume, image, or permissions are unavailable, affected operations stop and report the blocker. Preflight does not create a replacement database, migrate data, or switch to legacy SQLite.

Product-work records

Vision, stories, PRDs, decisions, design specifications, issues, dispatch records, and verification belong in LinearBoard’s PostgreSQL-backed app. Do not maintain PM copies in the repository.

Engineering and visual artifacts

Code, tests, and configuration stay in the repository. The versioned React Native prototypes from both design commands stay in the local workspace. Approval and status stay in the app.

06 / Planning

create-milestones

Group stories into milestones

Writes milestones and a document
Prepare
The vision, confirmed scope, and existing milestones or stories.
Expect
Native milestones and one milestone-overview document containing grouped stories with stable US IDs, anchors, and a structural index.
Check
Check native records under Milestones. In the overview document, each story has core acceptance and belongs to one native milestone. The index matches the readable sections.
$linearboard create-milestones
Project context: <Project>.
Derive stories from the existing vision and group them by observable outcomes. Reuse existing milestone and story IDs. Do not invent dates.

Creates no UserStory issues or View. Preserves existing legacy story issues.

07 / Requirements

create-PRDs

Save linked PRDs and clarify decisions

Writes PRDs and a View; starts live QA
Prepare
The native milestone, grouped story sections with stable IDs, and confirmed product rules.
Expect
Linked ProductRequirement issues and a saved PRDs View. Expect one consequential question at a time, using a selectable question card when available or the Markdown format below.
Check
Verify the milestone, matching M/US labels, story links, and View membership. After each reply, verify the current rule and acceptance criteria in the owning PRD body and the answer in a native comment.
Example of the Markdown fallback for a PRD question

Owning PRD: Booking rules (example)

Question:

How long should an unfinished booking hold a slot?

Example:

A customer starts booking the last 4 p.m. slot, then briefly loses their connection while entering details.

Options

  • A: Release the slot immediately.
    • Advantages: Another customer can book it right away.
    • Disadvantages: The first customer may lose the slot while entering details.
  • B: Hold the slot for five minutes.
    • Advantages: The first customer has time to finish.
    • Disadvantages: Other customers may wait for an abandoned booking.
$linearboard create-PRDs <Project> <Milestone>
Use the grouped stories for this milestone, verify the saved PRDs and View, then ask the first unresolved question that affects behavior or acceptance.

New issues start in Backlog. Reply in the same conversation to continue. Open decisions stay open; no new QA document.

08 / Design

create-designs

Compare three brand directions and record the choice

Local proposals; documents after selection
Prepare
Existing design documents or a brief, scoped stories/PRDs, target platform, and the primary user journey.
Expect
Exactly three runnable React Native proposals and an in-app review menu. After explicit style selection, two linked Project Documents record the exact version: Design Overview and Screen and Interaction Specification.
Check
Launch the prototype on the scoped platform and open all three versions from its review menu. Try the main journey and return navigation with the same fixtures and target width. After selection, read back both documents and the recorded style rules.
$linearboard create-designs <Project> <Milestone>
Use existing design context or the supplied brief. Show three runnable React Native directions for the same journey and wait for my choice.
Continue in chat
Reply with the exact proposal and version, or ask for revisions. That reply continues this command. Style selection does not approve the complete set.

LinearBoard stays read-only until you select a version. Reuse a confirmed choice for the same scope/version. No Design issues, View, or production work.

09 / Design

create-visuals

Complete and review the selected design

React Native prototype; Design issues after approval
Prepare
The exact style/version recorded by create-designs and the scoped screen, component, and state inventory.
Expect
Versioned runnable React Native screens and an in-app review menu. After explicit complete-set approval, Design tickets with native Approved JPGs and a saved Designs View.
Check
Exercise each scoped screen and key state from the prototype review menu on the declared target. After approval, verify the exact screen and version, inherited approval, readable JPG previews, and View membership.
$linearboard create-visuals <Project> <Milestone>
Extend the recorded style to all scoped screens and states. Give me the launch instructions, review menu entries and exact versions for complete-set approval.

Keep prototype launch details in chat. Before complete-set approval, request screenshots separately. Exact JPGs registered to the approved set inherit Approved. Other attachment approvals stay with the user.

Expect
FrontEnd delivery issues, acceptance checks, source links, blocking dependencies, and a <Project>-FE View.

Prepare
Existing milestone FE/BE issues; optionally name exact IDs.
Expect
Ordered checkpoints with issue links, grouping rationale, blockers, and observable outcomes. One native Batch N label per selected eligible issue.
Check

13 / Delivery

dispatch

Implement the authorized delivery scope

Dispatches, implements, and independently verifies
Prepare
Ready FE/BE IDs or a Batch N resolved to exact IDs within the project and milestone, applicable approved visuals, and an accessible execution target.
Expect
Dispatch records, validated plans, implementation reports, and the reviewer’s independent evidence and verified ticket status.
Check
Verify the main flow through the actual app’s normal entry point. Report results, environment limits, and remaining checks; read back issues and dispatch records.
$linearboard dispatch <Project> <Milestone> <Issue IDs>
Check readiness and dispatch only these issues. Verify the delivered target independently, record the evidence, and read back the resulting ticket status.
Continue in chat
For a verified batch, keep Batch 1 in the command and explain dependency order in the handoff. Native batch labels suffice. Use exact IDs for an authorized subset or when no batch applies.

Preflight is read-only when blocked. At most three workers, each owning one issue. The TPM coordinates dispatch and integration. The assigned reviewer records evidence and updates the assigned ticket.

14 / Maintenance

debug

Record and verify fixes on BUG tickets

Writes BUG tickets; fixes unless triage-only
Prepare
A bug observation, expected behavior, and reproduction context or existing issue IDs.
Expect
The coding agent creates or reuses the owning BUG ticket and records the report there before investigating. After the fix it comments on that same ticket: Status, Why, Action, Check.
Check
Read back the report, expectation, links, and FE/BE View. Verify the agent’s result comment, independent review evidence, and resulting status.
$linearboard debug <Project> <Milestone> <Report or issue IDs>
Continue in chat
For recording only, add: “triage-only; do not implement.”

Triage-only stops after verifying the ticket and its matching FE or BE View. Create the View if it is missing. Disputed behavior or a new request goes through sync review.

15 / Maintenance

sync

Propose record changes before applying them

Read-only until explicit approval
Prepare
A milestone and optional scope, record IDs, or new request.
Expect
One proposed from/to block per affected record. After explicit approval, only the approved edits and their readback.
Check
Review scope, relationships, and acceptance criteria. If UI evidence updates are approved, capture missing or stale states from the actual app and verify images on the owning records.
$linearboard sync <Project> <Milestone> <Scope>
Show one proposed from/to block per affected record and wait for my approval.

Invocation starts the review. Wait for approval before any write, including comments and uploads. No implementation.

06 / Review

Distinguish saving, approval, and acceptance

What you seeWhat it meansWhat remains
A document or PRD was savedThe record exists. Scope decisions may remain open.Read back content, sources, and native relationships. Resolve gaps that affect later work.
A style version was selectedThe choice is recorded in both design documents.Complete the originally requested screens, components, and key states.
The complete design set was approvedThe user approved an exact screen/version inventory.Verify Design tickets, the Designs View, and native Approved JPGs for the exact screen versions.
DoneRequired checks passed on the specified target, and any explicit acceptance is recorded.The reviewer records evidence, sets Done in the app, and reads back the status.
TodoA test restriction prevents a required check.Record the affected criterion, evidence of the restriction, and what to retest.
In Progress / BlockedA required check failed or work is unfinished.Record the failure and route the issue back for a fix.
In ReviewReview is underway or an explicit acceptance decision is pending.Record the remaining check or the decision needed.

Check saved Views

PRDs, Designs, FE, and BE are persisted category Views. By default they appear as project tabs and span all project milestones and statuses. Use shared placement or narrower filters only when requested. Reuse existing custom Views and verify actual membership; an unsaved filter is not a saved View.

Find the records in the app

  • Documents: vision, optional technical baseline, grouped milestone/story overview, design overview, and screen/interaction specification.
  • Milestones: native milestone records. Story grouping remains in the overview document.
  • Issues and category Views: PRDs, Design tickets, FE/BE delivery issues, and BUG tickets.
  • Delivery beneath the selected project in the sidebar: separately saved batches and dispatch records. Filter issues by Batch N to see the labels applied by the batching command.
A worker report, passing tests, or a successful upload response alone does not prove the full flow. Independently inspect the actual app, source records, relationships, and applicable evidence.
07 / Examples

Walk through a PocketMap delivery

These milestones and results are examples. Send the prompts in Codex chat after loading the skill. Use your board’s actual names.

1. Turn a story into a testable rule

Assume M1 already has a grouped story for saving a place. Send this to create or reuse the linked PRD and start the clarification conversation.

$linearboard create-PRDs "PocketMap" "M1 — Save a place"
Ask me how the app should handle an attempt to save the same place twice.

Answer in the same chat, for example, “Keep one saved entry and show that it’s already saved.” Open the saved PRD and check that it links to the story and records the agreed rule and how to verify it.

2. Choose how much to take on

Suppose M1 and M2 both have their approved designs and lack frontend tickets. A Recommended next step block could suggest create-issues-FE. Choose the focused option to finish the save flow first, or the full option to prepare tickets for both milestones. If M2’s design is still awaiting approval, it stays out of the ready set.

$linearboard create-issues-FE "PocketMap" "M1 — Save a place"

For full scope, request the same command for each eligible milestone. The second invocation in this example is:

$linearboard create-issues-FE "PocketMap" "M2 — Find saved places"

Check the FE View for tickets with source links and acceptance criteria. Ticket creation and batching leave implementation for a separate dispatch.

3. Dispatch a verified batch and read the result

After the FE and BE issues exist and the board shows exactly the intended ready tickets under Batch 1, send:

$linearboard dispatch "PocketMap" "M1 — Save a place" Batch 1
Check the selected batch on the required target and record the result on each ticket.

For example, the reviewer confirms that a duplicate attempt creates no second entry. If the required phone check cannot run because the device is unavailable, the issue goes to Todo with the missing check and the condition for resuming. If the duplicate actually creates a second entry, the issue goes back for remediation. Read the recorded result and status on each issue.

08 / Troubleshooting

Common questions

Cannot find the project, team, or milestone?

Provide a uniquely identifying name or link. Codex follows all list pages and checks the destination before creating anything. Similar names are not grounds for a duplicate. A new product gets only the minimal project container needed for explicitly authorized outputs when destination and scope are clear.

Will repeating a command create duplicates?

The workflow should inspect current state and reuse matching documents, issues, and Views. The API does not deduplicate titles automatically. After partial success, retry only the missing work rather than replaying every creation.

What if an update has a version conflict?

Read the latest version and reconcile differences. Do not force an overwrite. Preserve history, relationships, and out-of-scope content.

Is a missing UserStories View a skipped step?

No new story issues or View are produced by the merged create-milestones workflow. Stories live in the grouped document. Existing UserStory issues and Views remain available as historical sources.

How do deletion and restore work?

Explicitly identify the records to remove. Preview the impact before moving them to recoverable trash. There is no archive concept. Restore required teams/projects/parents first. Permanent deletion requires the user’s manual confirmation in the app. This guide executes no deletion.

Why did a dispatch record not start a worker?

The app stores records and exposes the API. Codex orchestrates the command; the design commands produce interactive React Native prototypes; coding agents implement changes. Creating a dispatch row alone does not start a worker. Missing execution tools must be reported as a blocker.

What if the test or execution environment is unavailable?

Record the environment, affected criterion, observed restriction, and what to check next. A required check blocked by a test restriction goes to Todo with Not tested or Environment-blocked evidence. A product failure goes back for remediation.
