Hands-on guideline

用 LinearBoard

從願景、故事與 PRD，到設計、派工和驗收。每一步都有可複製指令、App 中應看到的產出，以及操作後的檢查方式。

01 / Workflow

從第一個缺口接續

這是參考路徑，不是一次送出的批次命令。每個寫入或執行步驟都由你單獨提出；已有合格產出就重用，不重跑。

構想→願景→里程碑＋故事文件→PRDs→設計規格→完整視覺核准→FE／BE 開發票→派工→交審與驗收

只有構想

先 planning；確認後保存願景，再從故事分組建立里程碑。不要直接要求 dispatch。

已經有需求或工程進度

先讀目前紀錄，找第一個缺少的交付物。PRD 有重大未決問題才進行 prd-demystify；多張就緒票需要排序時才 organize-task-batch。

經確認的 BE-only 或非視覺範圍，可略過不適用的設計階段；這個判斷必須有需求紀錄依據。
02 / Setup

先替換佔位符

以下是貼到 Codex 的 skill 指令，不是 Terminal 指令。指南只產生文字，不會呼叫 API、啟動派工或修改你的專案。

<Team> / <Project> / <Milestone>
<Issue IDs> · <Repo path> · <App URL or run target>
  • <Project> 是 LinearBoard 的專案名稱；<Repo path> 才是工程目錄。
  • <Milestone> 請填實際里程碑名稱或可唯一解析的 ID，不要假設第一個就是 M1。
  • <Issue IDs> 請填從 App 讀到的確切識別碼。送出前替換所有剩餘佔位符。

啟動與儲存

預設應用程式位址為 http://127.0.0.1:8765。透過 operate.py 執行時會先檢查服務；已啟動就沿用，未啟動時檢查既有 Docker Compose、secret 與 PostgreSQL volume，再啟動服務。使用 connected MCP tools 前，Codex 先執行相同 preflight。

若既有部署、volume、image 或權限不可用，受影響操作會停止並回報。啟動檢查不會另建資料庫、遷移資料或改用舊 SQLite。

產品工作紀錄

願景、故事、PRD、決策、設計規格、票、派工與驗證，保存到 LinearBoard 的 PostgreSQL。工程目錄不另存 PM 文件副本。

工程與視覺產物

程式、測試、設定保留在 repo。create-visuals 的唯讀 HTML gallery 與 imagegen 原圖可保留，供視覺審閱；核准與狀態仍以 App 紀錄為準。

討論

03 / 規劃

create-vision-document

保存產品願景

寫入文件
準備
已確認的 planning 結論與目的地 <Team>／<Project>。
產出
原生 Vision Project Document，整理 4W1H、價值、邊界與假設。
檢查
在「文件」開啟願景，確認專案、內容與可存取的文件連結。
$linearboard create-vision-document <Project>
團隊：<Team>
依據以上已確認的 planning 結論建立或重用願景文件。保留尚未確認的假設。

不建立里程碑、故事票或開發票。

04 / 規劃

create-milestones

從故事分組成里程碑

寫入里程碑與文件
準備
願景、已確認範圍與既有里程碑／故事。
產出
原生 milestones ＋一份按里程碑分組的故事總覽文件；故事有穩定 US ID、anchor 與結構索引。
檢查
「里程碑」可見原生紀錄；「文件」中每則故事有核心驗收且只歸屬一個原生 milestone。索引與可讀段落一致。
$linearboard create-milestones <Project>
依據既有願景產生故事並按可觀察成果分組。重用既有里程碑與故事 ID，不虛構日期。

不建立 UserStory issues 或 UserStories View；已有舊故事票保留。

05 / 需求

create-PRDs

建立可追溯的產品規則

寫入 PRD issues 與 View
準備
<Milestone> 的故事文件、穩定 US ID 與已確認規則。
產出
ProductRequirement issues、來源文件／故事連結、原生 milestone 與 <Project>-PRDs saved View。
檢查
開啟 PRD：來源故事能對上文件段落；原生 milestone 正確；來源索引含真實 document ID 與 story IDs；View 包含預期 PRDs。
$linearboard create-PRDs <Project> <Milestone>
依據該里程碑的分組故事建立或重用 PRDs，保留待決問題；建立或重用 PRDs View 並驗證成員。

新票 Backlog；M／US labels 是選用輔助，保留既有標籤。文件段落不偽造為 issue relations。

06 / 需求

prd-demystify

直接釐清並修訂 PRD

更新原 PRD
準備
現有 PRDs、來源故事與尚未決定的產品範圍／邊界。
產出
使用者確認後，直接更新擁有該規則的 PRD；需要時保留原生留言。
檢查
一次回答一個關鍵問題後，重開 PRD 檢查行為與驗收已反映答案；未回答的問題仍標示未決。
$linearboard prd-demystify <Project> <Milestone>
先檢查既有答案，只問會影響產品範圍或驗收的未決問題，一次一題，確認後直接更新原 PRD。

不新增 QA 文件，不重寫既有歷史 QA，也不改 issue 狀態。

07 / 設計

create-designs

保存設計方向與互動規格

寫入兩份文件
準備
來源故事、PRDs、已確認決策與可用參考。
產出
設計總覽、畫面／互動規格兩份 Project Documents，包含具產品特色的方向與具體建議。
檢查
在「文件」檢查兩份規格互連；screen／flow 可追到需求；入口、操作與 loading／empty／error 等適用狀態清楚。
$linearboard create-designs <Project> <Milestone>
參考：<Design references>
限制與偏好：<Design constraints>
研究參考後提出設計建議，保存設計總覽與畫面／互動規格。

這一步只有文件，不產圖、不建立 Design tickets／View。

08 / 設計

create-visuals

從版型比較到完整視覺審閱

產圖；授權後上傳與建票
準備
既有設計規格、這次的畫面／元件／狀態範圍與已核准方向。
產出
imagegen studies、可開啟的唯讀 gallery；完整設計核准後建立或重用 Design tickets 與 <Project>-Designs View。
檢查
先核對生成範圍與批次，再檢查每張圖與 gallery；選定版型後補齊完整範圍。核准後讀回附件、Design tickets 與 View。
$linearboard create-visuals <Project> <Milestone>
本次範圍：<Screens, components and key states>
先說明覆蓋範圍與批次。新構圖比較適量代表版型；若是已選版型的小修，直接修訂。保留 imagegen 原圖。
接續對話範例
選定版型後可回覆：「選 <Layout>，繼續原先指定的完整畫面與狀態範圍。」 上傳時明說：「上傳 <Exact versions> 到所屬規格文件。」 完整審閱後明說：「核准 <Exact screen/version inventory> 的完整設計範圍，建立或重用 Design tickets 與 View。」 原生附件 approved 欄位仍由使用者在 App 操作；Codex 不代填。

新構圖通常比較 2–3 版代表畫面；小修直接改選定版型。選版、上傳、完整設計核准、附件原生核准分開。

09 / 交付

create-issues-FE

拆出前端交付責任

寫入 FE issues 與 View
準備
來源故事、PRDs、設計規格、確切核准的視覺版本與 <Repo path>。
產出
FrontEnd delivery issues、驗收、來源、阻擋相依與 <Project>-FE View。
檢查
任務可獨立審閱；路由、狀態、資料效果與 UI 驗證目標清楚。確切視覺參照能從 issue 開啟。
$linearboard create-issues-FE <Project> <Milestone>
工程目錄：<Repo path>
根據既有來源與核准視覺建立或重用 FE issues、相依與 FE View。缺少必要來源就回報，不派工。

新票 Backlog；保留既有狀態。不自動建立 BE 或派工。技術查核在此指令內進行。

10 / 交付

create-issues-BE

拆出資料與服務責任

寫入 BE issues 與 View
準備
來源故事、PRDs、資料／服務邊界與既有工程實作。
產出
BackEnd delivery issues、共用契約 owner、相依與 <Project>-BE View。
檢查
檢查資料一致性、錯誤／重試／復原、權限與可觀察驗收；共用規則有單一負責票。
$linearboard create-issues-BE <Project> <Milestone>
工程目錄：<Repo path>
資料／服務邊界：<Confirmed data and service scope>
先查核現有實作與官方文件，建立或重用 BE issues 與 BE View，不派工。

BE 可能是 App 內資料／服務，不預設新增雲端或伺服器。新票 Backlog，不派工。

11 / 交付

organize-task-batch

提議可審閱的交付批次

唯讀
準備
既有 FE／BE issues、來源與依賴；可指定 <Issue IDs>。
產出
聊天中的順序提案：Batch Name、FE Issues、BE Issues、分組原因、Expected Checkpoint Outcomes。
檢查
每張選定票恰好出現一次或有排除理由；checkpoint 有可觀察成果與前置條件。
$linearboard organize-task-batch <Project> <Milestone> <Issue IDs>
依既有相依提出可審閱 checkpoints，列出排除項與阻擋；只提案，不寫入或派工。
接續對話範例
若想把提案保存到 App 的「交付」頁，另行明確要求：「將剛確認的 <Batch proposal> 保存為 <Project> 的交付批次，保留確切 issue IDs；不要派工。」

不保存 batch、不修改票、不實作。批次大小不等於三個 worker 上限。

12 / 交付

dispatch

實作指定的交付範圍

派工、實作與獨立驗證
準備
明確 issue IDs 或已存在、可解析的 Batch；必要來源、設計、工程目錄與實際執行目標。
產出
派工紀錄、通過檢查的 worker 計畫、實作回報、TPM 獨立證據；可供審閱的工作到 In Review。
檢查
從實際 App 正常入口驗證主要流程；報告結果、環境限制與 remaining checks，並讀回 issue 與派工紀錄。
$linearboard dispatch <Project> <Milestone> <Issue IDs>
工程目錄：<Repo path>
實際驗證目標：<App URL or run target>
只派工指定 IDs，先核對來源、相依、核准設計與可存取的執行目標。驗證後交審，不改 Done。
接續對話範例
使用已保存批次時，第一行可改成： $linearboard dispatch <Project> <Milestone> Batch <Batch number> Batch 必須已存在且能解析確切 IDs；前一步的唯讀提案不代表它已保存。

先做 readiness preflight；缺必要資料就停在缺口。最多三個並行 workers，worker 不寫 LinearBoard。Done 由使用者決定。

13 / 維護

debug

從問題回報到修復驗證

預設包含修復
準備
<Report document URL or issue IDs>、重現步驟、預期行為與環境。
產出
Bugs Project Document 中的 Datetime／User Report、對應 FIX issues、FE／BE View、驗證證據與 Bugs 文件結果留言。
檢查
FIX 指向正確回報批次／項目；Bugs 文件原生留言回連 FIX 與結果。不能只有 issue 而沒有回報日誌。
$linearboard debug <Project> <Milestone> <Report document URL or issue IDs>
重現：<Reproduction steps>
預期：<Expected behavior>
環境：<Target environment>
記錄回報、建立或重用 bounded FIX issues，修復並獨立驗證。
接續對話範例
這次若只想整理問題，將最後一行改為：「triage-only：只記錄回報與建立／重用 FIX issues，不實作、不宣稱已修復。」

只做分類建票時必須指定 triage-only。預設會實作與驗證；不把問題記錄留成本機 PM 檔案。

14 / 維護

sync

對齊已確認的紀錄與 UI 證據

更新限定範圍
準備
<Scope>、已確認來源、受影響 issue／規格與目前 UI。
產出
差異與已驗證更新；涉及 UI 變動時，補齊／更新實際 UI 截圖、附件與 owning specification index。
檢查
分開回報 Updated／Already aligned／Conflict／Unverified；截圖分 Missing／Stale／Consistent／Unverified。讀回內容、關聯與圖像。
$linearboard sync <Project> <Milestone> <Scope>
只對齊以上範圍的已確認紀錄。若 UI 已改動，檢查截圖是否缺漏或過時，從實際介面擷取並驗證上傳。保留歷史，不實作。

不實作、不以 imagegen 代替實際截圖、不自動改狀態／核准、不因時間較新就覆蓋。清理圖片須另有授權。

06 / Review

分清儲存、核准與驗收

看到的結果代表什麼還要做什麼
文件／PRD 已保存紀錄存在，可能仍有未決範圍。讀回內容、來源與原生關聯；先處理影響後續交付的缺口。
已選版型只確定構圖方向。繼續原定完整畫面、元件與關鍵狀態。
完整設計已核准確切畫面／版本範圍有使用者核准紀錄。驗證 Design tickets、Designs View 與可存取的 exact references；附件原生欄位單獨回報。
In Review實作完成並經 TPM 獨立檢查，可以交給使用者審閱。使用者操作並決定是否接受；環境限制與未測項仍要明列。
Done最終使用者接受交付。由使用者決定並在 App 操作；Codex 不代替決定。

Saved Views 檢查

PRDs、Designs、FE、BE 是實際保存的分類 View，預設位於專案上方分頁，跨該專案的所有里程碑與狀態；使用者指定時才放在 shared 或縮小範圍。重用既有自訂 View，核對實際成員，不能把臨時 filter 當成 saved View。

在 App 找到紀錄

  • 「文件」：願景、分組故事總覽、設計總覽與畫面互動規格、Bugs 回報日誌。
  • 「里程碑」：原生 milestone；故事分組仍在總覽文件。
  • 「任務」與分類 Views：PRDs、Design tickets、FE／BE 與 FIX issues。
  • 側欄目前專案下的「交付」：已保存批次與派工紀錄。唯讀批次提案不會自動出現在這裡。
worker 回報、綠色測試結果或上傳成功回應，都不能單獨證明整個流程通過。主 App、實際來源／關聯與適用證據必須獨立檢查。
07 / Troubleshooting

常見問題

找不到專案、團隊或里程碑？

提供可唯一識別的名稱或連結。Codex 先完整分頁查找並核對目的地，不能因同名就直接建立副本。新產品只有在目的地與授權產出明確時，才建立必要的專案容器。

重複送出，會不會重複建票？

指令應先讀現況，重用相同目的與來源的文件、票與 View；API 同名不會自動去重。部分成功時只補缺少的工作，不重播全部建立步驟。

更新時出現版本衝突？

重新讀取最新版本並對齊差異，不強行覆蓋。歷史、關聯與範圍外內容都保留。

沒有 UserStories View，是否少做一步？

新版 create-milestones 把故事保存在分組文件中，不建立新故事票或 View。既有 UserStory issues／Views 可作歷史來源保留。

刪除與還原怎麼辦？

需明確指定要刪除的紀錄；先預覽影響，再移到可還原的垃圾桶。沒有封存概念。還原需要的團隊／專案／父項先存在；永久刪除由使用者在 App 手動確認。本指南不會執行刪除。

Skill 沒有真的派工或操作外部工具？

App 保存紀錄與提供 API；Codex 負責命令流程，imagegen 負責視覺生成，coding agents 負責實作。單純建立 dispatch row 不會啟動 worker；缺少必要工具時必須回報阻擋。

測試或執行環境不可用？

報告確切環境、受影響驗收與已驗證範圍。未測項保持 Not tested／Environment-blocked。核心流程未驗證或產品仍有問題時，不能宣稱可交審；只有證據明確歸因於狹窄環境限制的情況，才依 skill 規則列明限制後交審。
