Hands-on guideline

從願景、故事與 PRD，到設計、派工和驗收。每一步都有可複製指令、App 中應看到的產出，以及操作後的檢查方式。

01 / Workflow

從第一個缺口接續

這是參考路徑，不是一次送出的批次命令。每個寫入或執行步驟都由你單獨提出；已有合格產出就重用，不重跑。

構想→願景→技術基線（如需要）→里程碑與分組故事→PRDs 與逐題釐清→三個方案與風格選擇→完整核准與 Design 票→FE／BE 票→批次標籤（如需要）→派工→審閱與驗收

從構想開始

先用 planning 討論構想。保存願景後，視需要記錄共用技術限制，再建立里程碑與分組故事。

延續既有工作

重用已驗證產出。已確認的純後端或非視覺範圍可略過設計。若你明確選擇已核准的靜態圖，且可存取的 JPG 與核准紀錄涵蓋確切範圍及版本，也可略過原型步驟。確切的交付範圍通過就緒檢查後才派工。

回覆末尾的 Recommended next step 會說明如何接續待定事項，或建議下一個指令及理由。同一指令若有重點與完整兩種有意義的範圍，會列出可執行的選項，由你決定。看實作範例。
02 / Setup

先替換佔位符

以下是貼到 Codex 的 skill 指令，不是 Terminal 指令。指南只產生文字，不會呼叫 API、啟動派工或修改你的專案。

<Team> / <Project> / <Milestone>
<Issue IDs> · <Repo path> · <App URL or run target>
  • <Project> 是 LinearBoard 的專案名稱；<Repo path> 才是工程目錄。
  • <Milestone> 請填實際里程碑名稱或可唯一解析的 ID，不要假設第一個就是 M1。
  • <Issue IDs> 請填從 App 讀到的確切識別碼。送出前替換所有剩餘佔位符。

啟動與儲存

預設應用程式位址為 http://127.0.0.1:8765。透過 operate.py 執行時會先檢查服務；已啟動就沿用，未啟動時檢查既有 Docker Compose、secret 與 PostgreSQL volume，再啟動服務。使用 connected MCP tools 前，Codex 先執行相同 preflight。

若既有部署、volume、image 或權限不可用，受影響操作會停止並回報。啟動檢查不會另建資料庫、遷移資料或改用舊 SQLite。

產品工作紀錄

願景、故事、PRD、決策、設計規格、票、派工與驗證，保存到 LinearBoard 的 PostgreSQL。工程目錄不另存 PM 文件副本。

工程與視覺產物

程式碼、測試與設定留在儲存庫。兩個設計指令的 React Native 原型留在本機；核准及狀態留在 App。

05 / Practice

逐步操作與讀回檢查

每次選一個適用步驟。送出後依「檢查」開啟 App 產出，再決定下一步；複製指令本身不代表已執行。

01 / 起步

init

設定儲存庫指引與代理

本機工程檔案
準備
確切專案及其程式碼儲存庫，必要時提供路徑。
產出
建立或安全更新 AGENTS.md 與專案 Codex 代理。
檢查
檢查本機差異及代理清單、角色和支援指令，確認保留自訂指引。
$linearboard init <Project>

不改產品紀錄、不推進交付階段，也不安裝 hooks。

02 / 起步

help

查看可用指令

唯讀
準備
已安裝的 skill；不需要啟動 App 或選擇專案。
產出
只有指令及用途清單。
檢查
核對回傳語法與指令索引。故事指令是相容別名。
$linearboard help

不寫入應用程式，也不執行後續步驟。

03 / 規劃

planning

整理產品構想

討論
準備
<Product idea>、<Target user>、<Constraints>。
產出
聊天中的產品問題、價值、範圍與待驗證假設。若已選技術，會依官方來源初步確認能否支援核心流程。
檢查
你能指出產品服務誰、解決什麼問題，以及這輪不做什麼。
$linearboard planning
專案背景：<Project>。
產品構想：<Product idea>
目標使用者／玩家：<Target user>
限制：<Constraints>
先討論方向，不保存紀錄。

只有明確要求保存，才會寫入 LinearBoard。

04 / 規劃

create-vision-document

保存產品願景

寫入文件
準備
已確認的 planning 結論與目的地 <Team>／<Project>。
產出
依已確認的 4W1H 建立原生 <Project> — Product Vision 文件。
檢查
在「文件」開啟願景，確認專案、內容與可存取的文件連結。
$linearboard create-vision-document
專案背景：<Project>。
團隊：<Team>
依據以上已確認的 planning 結論建立或重用願景文件。保留尚未確認的假設。

不建立里程碑、故事票或開發票。

05 / 規劃

create-technical-baseline

記錄共用技術限制

寫入一份專案文件
準備
已保存的願景、已選技術或共用限制，以及相關官方來源。
產出
專案層級的 <Project> — Technical Baseline，記錄可行性、限制、建議檢查與未決事項。
檢查
確認原生專案歸屬，並區分文件查核與實際測試。
$linearboard create-technical-baseline <Project>

有共用限制需要保存時才使用。功能專屬的技術決策記在對應 FE 或 BE 票。

06 / 規劃

create-milestones

從故事分組成里程碑

寫入里程碑與文件
準備
願景、已確認範圍與既有里程碑／故事。
產出
原生 milestones ＋一份按里程碑分組的故事總覽文件；故事有穩定 US ID、anchor 與結構索引。
檢查
「里程碑」可見原生紀錄；「文件」中每則故事有核心驗收且只歸屬一個原生 milestone。索引與可讀段落一致。
$linearboard create-milestones
專案背景：<Project>。
依據既有願景產生故事並按可觀察成果分組。重用既有里程碑與故事 ID，不虛構日期。

不建立 UserStory issues 或 View；已有舊故事票保留。

07 / 需求

create-PRDs

保存關聯 PRDs 並逐題釐清

寫入 PRDs 與 View；開始即時問答
準備
原生里程碑、有穩定 ID 的分組故事，以及已確認的產品規則。
產出
具來源連結的 ProductRequirement issues 與已保存的 PRDs View。接著一次問一個關鍵問題，優先使用可選答案卡片，否則使用 Markdown 問答格式。
檢查
核對里程碑、M／US 標籤、故事連結與 View 成員。每次回答後，核對原 PRD 內文的規則及驗收條件，以及原生留言中的答案。
範例：PRD 問答的 Markdown 格式

對應 PRD：預約規則（範例）

Question:

尚未完成的預約應保留時段多久？

Example:

顧客開始預約最後一個下午四點的時段，填寫資料時網路短暫中斷。

Options

  • A: 立即釋出時段。
    • Advantages: 其他顧客可立即預約。
    • Disadvantages: 原顧客填寫資料時可能失去時段。
  • B: 保留時段五分鐘。
    • Advantages: 原顧客有時間完成預約。
    • Disadvantages: 其他顧客可能要等待已放棄的預約過期。
$linearboard create-PRDs <Project> <Milestone>
使用此里程碑的分組故事，核對保存的 PRDs 與 View，再詢問第一個會影響行為或驗收的未決問題。

新票從 Backlog 開始。在同一段對話回覆即可接續。未回答的決策維持未定，不另建 QA 文件。

08 / 設計

create-designs

比較三種品牌方向並記錄選擇

本機提案；選定後寫入文件
準備
既有設計文件或 brief、適用故事與 PRDs、目標平台及主要使用流程。
產出
正好三個可操作的 React Native 方案，從原型內的審閱選單切換。明確選定風格後，於互相連結的 Design Overview 與 Screen and Interaction Specification 記錄確切版本。
檢查
在指定平台啟動原型，從審閱選單開啟三版，以相同範例資料與目標尺寸操作主要流程及返回路徑。選定後讀回兩份文件及風格規則。
$linearboard create-designs <Project> <Milestone>
使用既有設計背景或提供的 brief，展示同一操作流程的三個可操作方向，等我選擇。
接續對話
回覆確切方案與版本，或要求修訂，即可接續此指令。選定風格不等於核准完整設計。

選定版本前 LinearBoard 維持唯讀。同範圍及版本可重用已確認方向。不建 Design 票、不建 View、不改正式程式。

09 / 設計

create-visuals

完成並審閱選定的設計

React Native 原型；核准後建立 Design 票
準備
create-designs 已記錄的確切風格及版本，以及範圍內畫面、元件及狀態清單。
產出
有版本的 React Native 畫面與原型內的審閱選單。明確核准全套設計後，建立含原生 Approved JPG 的 Design 票與 Designs View。
檢查
在指定平台從原型的審閱選單操作各畫面及關鍵狀態。核准後核對畫面及版本、繼承的核准、各票 JPG 預覽及 View 成員。
$linearboard create-visuals <Project> <Milestone>
將已記錄的風格延伸到所有指定畫面與狀態，提供啟動方式、審閱選單與確切版本清單供完整核准。

原型連結留在對話中。完整設計核准前，截圖須另行要求。對應核准範圍的確切 JPG 會繼承 Approved，其餘附件核准由使用者操作。

10 / 交付

create-issues-FE

拆出前端交付責任

寫入 FE issues 與 View
準備
來源故事、PRDs、設計規格、確切核准的視覺版本與 <Repo path>。
產出
FrontEnd delivery issues、驗收、來源、阻擋相依與 <Project>-FE View。
檢查
任務可獨立審閱；路由、狀態、資料效果與 UI 驗證目標清楚。確切視覺參照能從 issue 開啟。
$linearboard create-issues-FE <Project> <Milestone>
工程目錄：<Repo path>
根據既有來源與核准視覺建立或重用 FE issues、相依與 FE View。缺少必要來源就回報，不派工。

新票 Backlog；保留既有狀態。不自動建立 BE 或派工。技術查核在此指令內進行。

11 / 交付

create-issues-BE

拆出資料與服務責任

寫入 BE issues 與 View
準備
來源故事、PRDs、資料／服務邊界與既有工程實作。
產出
BackEnd delivery issues、共用契約 owner、相依與 <Project>-BE View。
檢查
檢查資料一致性、錯誤／重試／復原、權限與可觀察驗收；共用規則有單一負責票。
$linearboard create-issues-BE <Project> <Milestone>
工程目錄：<Repo path>
資料／服務邊界：<Confirmed data and service scope>
先查核現有實作與官方文件，建立或重用 BE issues 與 BE View，不派工。

BE 可能是 App 內資料／服務，不預設新增雲端或伺服器。新票 Backlog，不派工。

12 / 交付

organize-task-batch

依相依關係分批並加上標籤

寫入 Batch N 議題標籤
準備
此里程碑的既有 FE／BE 票，可選填確切 IDs。
產出
有順序的交付檢查點，包含議題連結、分組理由、阻礙及可觀察成果。每張符合條件的選定議題加上一個原生 Batch N 標籤。
檢查
依團隊、專案、原生里程碑及 Batch N 篩選兩個分類，核對確切 IDs，確認保留其他標籤及狀態。
$linearboard organize-task-batch <Project> <Milestone> <Issue IDs>
依可審閱成果將選定的交付票分批，套用 Batch N 標籤並核對成員。不派工。

說明「只預覽」即不寫入。獨立的交付批次紀錄須明確要求。分批不會派工。

13 / 交付

dispatch

實作指定的交付範圍

派工、實作與獨立驗證
準備
已就緒的 FE／BE IDs，或能在專案與里程碑內解析成確切 IDs 的 Batch N；另需適用的已核准視覺及可操作的執行目標。
產出
派工紀錄、已確認的實作計畫、實作回報，以及審閱者的獨立驗證證據與讀回確認的任務狀態。
檢查
從實際 App 正常入口驗證主要流程；報告結果、環境限制與 remaining checks，並讀回 issue 與派工紀錄。
$linearboard dispatch <Project> <Milestone> <Issue IDs>
先確認就緒，再派送指定任務。獨立驗證實際交付目標，記錄證據，最後讀回任務狀態。
接續對話
批次通過核對後，指令保留 Batch 1，並在交接中說明相依順序。原生批次標籤即可。已授權的部分議題或無適用批次時，使用確切 IDs。

未就緒時只做唯讀檢查。最多三位實作者，各負責一張任務。TPM 協調派工與整合；指定審閱者記錄證據並更新所負責的任務狀態。

14 / 維護

debug

在 BUG 票記錄並驗證修復

寫入 BUG 票；只分流時不修復
準備
問題觀察、預期行為及重現背景，或既有 issue IDs。
產出
coding agent 先建立或重用對應 BUG 票並記錄回報，再調查。修復後在同一張票留言：Status、Why、Action、Check。
檢查
讀回回報、預期、來源連結與 FE／BE View。確認實作者的結果留言、獨立審閱證據及更新後的狀態。
$linearboard debug <Project> <Milestone> <Report or issue IDs>
接續對話
若只記錄，補充：「triage-only；不實作。」

只分流時，核對 BUG 票及對應 FE 或 BE View 後停止。若 View 缺少則建立。行為有爭議或新增需求時，走 sync 審閱。

15 / 維護

sync

先提議紀錄變更，再依核准套用

明確核准前維持唯讀
準備
指定里程碑，可選填範圍、紀錄 IDs 或新需求。
產出
每筆受影響紀錄一組 from/to 提案。明確核准後，只套用已核准的變更並讀回。
檢查
檢查範圍、關聯及驗收條件。若已核准更新 UI 證據，從實際 App 擷取缺漏或過時狀態，並在對應紀錄驗證圖片。
$linearboard sync <Project> <Milestone> <Scope>
每筆受影響紀錄列出一組 from/to 提案，等我核准。

執行指令只啟動審閱。任何寫入（含留言、上傳）都須先核准。不實作。

06 / Review

分清儲存、核准與驗收

看到的結果代表什麼還要做什麼
文件／PRD 已保存紀錄存在，可能仍有未決範圍。讀回內容、來源與原生關聯；先處理影響後續交付的缺口。
已選風格版本選擇已記錄於兩份設計文件。繼續原定完整畫面、元件與關鍵狀態。
完整設計已核准確切畫面／版本範圍有使用者核准紀錄。核對 Design 票、Designs View 與各畫面版本的原生 Approved JPG。
Done指定目標的必測項目皆通過，明訂的使用者驗收也已記錄。審閱者記下證據，從 App 介面設定 Done，再確認狀態。
Todo測試限制使必測項目無法執行。記下受影響的條件、限制的證據與下次要驗證的項目。
In Progress / Blocked必測項目失敗，或實作尚未完成。記下失敗結果，交回修正。
In Review仍在審閱，或等待任務明訂的驗收決定。記下尚待完成的檢查或需要的決定。

Saved Views 檢查

PRDs、Designs、FE、BE 是實際保存的分類 View，預設位於專案上方分頁，跨該專案的所有里程碑與狀態；使用者指定時才放在 shared 或縮小範圍。重用既有自訂 View，核對實際成員，不能把臨時 filter 當成 saved View。

在 App 找到紀錄

  • 「文件」：願景、選用的技術基線、分組故事總覽、設計總覽及畫面互動規格。
  • 「里程碑」：原生 milestone；故事分組仍在總覽文件。
  • 「任務」與分類 Views：PRDs、Design tickets、FE／BE 與 BUG tickets。
  • 側欄目前專案下的「交付」：另外保存的批次與派工紀錄。分批指令套用的 Batch N 標籤可在議題清單篩選。
worker 回報、綠色測試結果或上傳成功回應，都不能單獨證明整個流程通過。主 App、實際來源／關聯與適用證據必須獨立檢查。
07 / Examples

從 PocketMap 故事走到交付

以下里程碑和結果都是範例。載入 skill 後在 Codex 對話貼上指令，並換成看板上的實際名稱。

1. 把故事變成可驗證的規則

假設 M1 已有儲存地點的分組故事。送出指令，建立或重用連到故事的 PRD，再接著釐清規則。

$linearboard create-PRDs "PocketMap" "M1 — Save a place"
請先問我，同一個地點再儲存一次時，App 應該怎麼處理。

在同一對話回答，例如「只保留一筆，並提示已儲存」。再到 PRD 確認故事連結、議定規則及驗收方法都有保存。

2. 選擇這次要處理多少工作

假設 M1 和 M2 的設計都已核准，前端任務也都還沒建立。Recommended next step 可能建議 create-issues-FE。想先做完儲存流程，就選 M1；想先準備兩個里程碑的任務，就選完整範圍。若 M2 的設計仍待核准，先只做 M1。

$linearboard create-issues-FE "PocketMap" "M1 — Save a place"

完整範圍會對每個已就緒的里程碑執行同一指令。本例的第二個指令是：

$linearboard create-issues-FE "PocketMap" "M2 — Find saved places"

在 FE View 核對新任務的來源連結與驗收條件。建票和分批完成後，再另外下達派工指令。

3. 派工給已確認的批次，再讀回結果

前後端任務建立後，確認 Batch 1 只包含這次要做、且已就緒的任務，再輸入：

$linearboard dispatch "PocketMap" "M1 — Save a place" Batch 1
請在指定目標驗證這批任務，並將結果寫到各自的票上。

例如審閱者確認重複儲存沒有多一筆資料，但必測的手機不在手邊，會把任務移到 Todo 並記下要補測的項目與條件。若實際上多出一筆，則交回修正。到各任務查看證據與更新後的狀態。

08 / Troubleshooting

常見問題

找不到專案、團隊或里程碑？

提供可唯一識別的名稱或連結。Codex 先完整分頁查找並核對目的地，不能因同名就直接建立副本。新產品只有在目的地與授權產出明確時，才建立必要的專案容器。

重複送出，會不會重複建票？

指令應先讀現況，重用相同目的與來源的文件、票與 View；API 同名不會自動去重。部分成功時只補缺少的工作，不重播全部建立步驟。

更新時出現版本衝突？

重新讀取最新版本並對齊差異，不強行覆蓋。歷史、關聯與範圍外內容都保留。

沒有 UserStories View，是否少做一步？

新版 create-milestones 把故事保存在分組文件中，不建立新故事票或 View。既有 UserStory issues／Views 可作歷史來源保留。

刪除與還原怎麼辦？

需明確指定要刪除的紀錄；先預覽影響，再移到可還原的垃圾桶。沒有封存概念。還原需要的團隊／專案／父項先存在；永久刪除由使用者在 App 手動確認。本指南不會執行刪除。

Skill 沒有真的派工或操作外部工具？

App 保存紀錄與提供 API；Codex 負責命令流程，設計指令產出可操作的 React Native 原型，coding agents 負責實作。單純建立 dispatch row 不會啟動 worker；缺少必要工具時必須回報阻擋。

測試或執行環境不可用？

記錄環境、受影響的驗收項目、實際限制與下次驗證動作。必測項目因測試限制無法執行時，標記 Not tested 或 Environment-blocked，任務回到 Todo。若驗證失敗是產品問題，就交回修正。
