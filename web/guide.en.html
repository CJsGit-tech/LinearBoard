LinearBoard user guide

Back to workspace · Repository and setup

LinearBoard keeps product work in a local workspace. Use the sidebar's Language selector to choose English or Traditional Chinese. Your language choice stays in this browser. Changing it does not translate project content or change the database.

Start a project

  1. Choose Create project in an empty workspace or the + beside Projects.
  2. Enter a project name, select a team, and add a description if needed.
  3. Save. Use the project tabs to open Overview, Issues, Documents, and Milestones.
  4. Add milestones with an expected outcome and an optional target date. Avoid inventing commitments that have not been agreed.

In Workspace settings → Team, you can create teams and edit their workflow states, one per line. Referenced states cannot be removed. Existing custom state names stay exactly as entered.

Work with issues

Choose New issue or press C outside an editor. Enter a title, category, state, milestone, and optional labels. The categories are User stories, PRDs, Design, FrontEnd, and BackEnd. Category is a dedicated single-select group.

Open an issue to read its body and edit its properties. More properties contains priority, assignee, and parent issue. Add source relations and blocking dependencies under Relations and dependencies. Parent and blocking relations cannot form cycles. Use Save changes to persist edits.

/ opens issue search outside editable controls. The filter button exposes category, state, and milestone filters. Switch between List view and Board view using the controls above the results. In a board grouped by status, drag an issue to another status column to change its state.

Select issue checkboxes for bulk actions. A bulk state update is atomic: if any selected issue has a stale version, no selected issues are changed. Reopen or reload the current data before retrying.

Save a View

Choose Add tab View in a project. Give it a name, choose filters and grouping, and place it in the issue tabs or shared sidebar. Filters combine with AND. Leaving the state selection empty includes all states. View membership reflects actual matching records.

Write documents and comments

Create documents from the Documents tab or the project overview. Choose a document type and optional milestone, then write rich text or Markdown. The toolbar supports headings, bold, italic, lists, tasks, code, links, undo, and redo.

Content containing HTML stays in Markdown mode so its source is preserved. Use Save document explicitly. Comments have their own Post comment action. Revision history retains earlier versions. Use Back or Alt+← to return from a record; reopening and navigation read current data from the app.

Attach files and record evidence

Under an issue or document, choose Add attachment. Upload a file up to 15 MB or provide an HTTP(S) link. Add screen and version identifiers where applicable. Images recognized as PNG or JPEG can display inline; other files are offered as downloads.

Review labels distinguish Draft, Approved, Superseded, and Verification evidence. For skill-driven design, exact JPGs registered against the user’s complete-set approval inherit Approved on their owning Design tickets. The user controls approval of other attachments. Keep prototype links in chat and link to the Approved JPGs from LinearBoard records. An uploaded image alone does not establish design approval or prove that a product was implemented.

Use Record verification to capture the criterion, environment, result, and observations. In a skill-led delivery review, the assigned reviewer records the evidence and applies the status. Use Done in the app when required checks pass and explicit acceptance gates are met. Use Todo when a test restriction blocks a required check. A product failure goes back for remediation. In Review covers review underway or an explicit acceptance decision still pending.

Delivery batches and dispatch records

Open Delivery under the selected project in the sidebar. For the app’s separate saved batch records, create batches from FrontEnd or BackEnd issues, recording the rationale, expected output, checks, and blockers. A dispatch covers one issue and records an execution target, scope, reviewed plan, worker report, and independent verification.

At most three dispatches may be active. The same issue cannot have duplicate active assignments. A reviewed plan is required before execution, and a completion report is required before marking a dispatch completed. These records do not run agents; execution and independent product inspection happen through external tools.

Trash and backups

Deletion first shows an impact preview. Moving an issue to trash includes its descendants; deleting a project includes its owned records. In Workspace settings → Trash, restore a deletion batch or permanently delete it. Restore required teams, projects, and parent records first. Permanent deletion cannot be undone; old backups may retain the data.

Use Download database backup in Workspace settings. Compose returns a PostgreSQL custom-format dump. SQLite development mode returns a SQLite backup. Restore into a separate empty database and verify it before switching. Do not remove the Docker volume when stopping the app.

Use the management skill

The repository includes the English LinearBoard skill. It is an instruction set for Codex, separate from the app's storage and UI. Product records stay in LinearBoard; the repository holds code, tests, and reusable skill instructions.

Command Purpose
init <Project> [repository path]Safely set up repository AGENTS.md and project agents. It does not write product records or install hooks.
helpList commands and purposes offline.
planningDiscuss the product and briefly check a chosen stack against official sources. Save only when requested.
create-vision-documentSave the 4W1H vision in a native Project Document.
create-technical-baseline <Project>Record shared technical requirements, feasibility, limits, and open decisions when needed.
create-milestonesCreate native milestones and a document with grouped user stories.
create-PRDs <Project> <Milestone>Save linked requirement issues and their View. Then clarify one decision at a time using a selectable question card when available. Verify the answer in the owning PRD body and comment.
create-designs <Project> <Milestone>Compare three runnable proposals. After explicit style selection, record the chosen version in both design documents.
create-visuals <Project> <Milestone>Extend the recorded style to the full scoped HTML set. After complete-set approval, verify Design tickets, their native Approved JPGs, and the Designs View.
create-issues-FE <Project> <Milestone>Create or revise frontend issues and their View. New issues start in Backlog.
create-issues-BE <Project> <Milestone>Create or revise backend issues and their View. New issues start in Backlog.
organize-task-batch <Project> <Milestone> [issue IDs]Order checkpoints, apply Batch N labels, and verify exact issue membership. Ask for preview-only to skip writes.
dispatch <Project> <Milestone> [Batch <n> | issue IDs]Check readiness, implement only the selected FE/BE issues, and independently verify the result.
debug [Project] [Milestone] [report or issue IDs]Have the coding agent record and investigate a defect on its BUG ticket and post the result there. Triage-only stops after verifying the ticket and its matching FE or BE View. Create the View if missing.
sync <Project> <Milestone> [scope or new request]Show one from/to proposal per affected record and wait for explicit approval before applying any changes.

Start at the first unfinished applicable step and reuse verified records. The final Recommended next step block tells you how to resume a pending decision or explains the next command. When both are useful, it gives focused and full options for the same command, covering only eligible work. You choose what to run.

For example, send $linearboard dispatch "PocketMap" "M1 — Save a place" Batch 1 in Codex chat after checking the batch membership. If saving works but the required phone is unavailable, expect the missing check and its resume condition on the issue, with status Todo.

Use the installed skill's instructions as the workflow authority. The API's capability catalog lists the supported commands and their data contracts. Codex runs the workflow and verifies each result. When you choose approved static visuals, proceed to delivery issues once accessible JPGs and recorded approval cover the exact scope and version.

MCP and API

Start the app, then configure python3 /absolute/path/to/LinearBoard/mcp_server.py --url http://127.0.0.1:8765 as a stdio server in your MCP client. Use Integration and commands to inspect tools and contracts.

List operations are paginated. Updates require the current expected_version. Reuse the same idempotency key and identical payload for a retry. API clients can request English validation errors with Accept-Language: en; record content remains unchanged.

This is a local application for its owner. Keep the service on loopback, retain the database password privately, and keep workspace databases and backups out of Git.
